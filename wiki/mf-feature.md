Learn how mf-feature runs a task in 10 minutes: its pieces, its loop, and where each file comes from.

mf-feature is an agent style. You start it with `/mf-feature <task>`. The agent then works in a fixed way: it states the goal, picks a playbook, routes parts of the work to skills, reads the principles it applies, delegates to subagents, verifies, and replies in a set format.

The text comes from poteto's [pstack](https://github.com/cursor/plugins/tree/main/pstack) (Lauren Tan, MIT). montflow imports it, renames it into the `mf-` namespace, and calls the result **mfstack**. Every word of it is generated by `scripts/import-mfstack.ts`. See [The import](#the-import).

## The pieces

| Piece | What it is | On disk | Read with |
| --- | --- | --- | --- |
| Entry skill | `mf-feature`: the non-negotiables, the principle index, autonomy rules, subagent rules, the reply style, the playbook list | `.agents/skills/mf-feature/SKILL.md` | `/mf-feature` |
| Worker brief | The rules every subagent follows, whatever its kickoff says | `.agents/skills/mf-feature/worker.md` | first line of each kickoff |
| Routed skills | 31 `mf-feature-*` skills: architect, swarm, arena, interrogate, unslop, no-comments, technical-writing, figure-it-out, how, why and more | `.agents/skills/mf-feature-<name>/SKILL.md` | `/mf-feature-<name>` or a trigger |
| Principles | 24 short rules, each with when it applies | `.agents/@montflow/principles/<name>/PRINCIPLE.md` | `mf-principles list`, `mf-principles show <name>` |
| Playbooks | 22 step lists for kinds of task, each naming the skills, principles and playbooks it uses | `.agents/@montflow/playbooks/<name>/PLAYBOOK.md` | `mf-playbooks list`, `mf-playbooks show <name>` |
| Profiles | `mf-feature-generic-worker` (the generic worker every delegating step spawns) and `mf-feature-comment-sicko` (the comment reviewer) | `.agents/@montflow/profiles/<name>/PROFILE.md` | `mf-profiles show <name>` |
| Roles | Which harness and model run each kind of subagent, as ordered preferences per seat | `.agents/@montflow/feature/roles.json`, git-ignored | `mf-feature roles`, `mf-feature roles resolve <role>` |
| Helper scripts | pstack's scripts, such as `watch-pr` and `worktree-audit.sh` | `.agents/skills/mf-feature/scripts/` | the skills that name them |

Skills are plain files in the skill store. Principles and playbooks each have their own store and CLI, so an agent can list them by one line each and read only the ones it needs.

## How the stores fit together

```mermaid
flowchart LR
    subgraph checkout["montflow checkout"]
        modePkg["packages/mf-feature<br/>skills/ + profiles/ + payload.json"]
        princPkg["packages/mf-principles<br/>principles/ + payload.json"]
        playPkg["packages/mf-playbooks<br/>playbooks/ + payload.json"]
    end
    subgraph workspace["your repository: .agents/"]
        skills[".agents/skills/<br/>mf-feature, mf-feature-*"]
        profiles[".agents/@montflow/profiles/<br/>mf-feature-generic-worker, mf-feature-comment-sicko"]
        princ[".agents/@montflow/principles/"]
        play[".agents/@montflow/playbooks/"]
    end
    modePkg -- "mf-feature doctor" --> skills
    modePkg -- "mf-feature doctor" --> profiles
    princPkg -- "mf-principles doctor" --> princ
    playPkg -- "mf-playbooks doctor" --> play
    agent(["agent in /mf-feature"])
    skills -- "reads SKILL.md, worker.md" --> agent
    princ -- "mf-principles list / show" --> agent
    play -- "mf-playbooks list / show" --> agent
    play -.->|verify resolves names| skills
    play -.-> princ
```

- The mode package ships the `mf-feature` and `mf-feature-*` skills and both profiles; `mf-feature doctor` installs them. `mf-skills sync` copies montflow's other public skills.
- Each package's `doctor` installs what its `payload.json` lists, nested folders such as a skill's `references/` and `scripts/` included. `doctor --check` reports drift and writes nothing.
- `mf-playbooks verify` fails when a playbook names a skill, principle or playbook that is not installed. Sync the skills before you verify the playbooks.
- In a repository that uses montflow, the `mf-*` names are not on `PATH`. Run them as `bun run --cwd <checkout>/packages/<pkg> cli <verb> --dir "$PWD"`. An agent can also read the store file directly.

## The lifecycle of a task

```mermaid
flowchart TD
    start(["/mf-feature {task}"]) --> goal["Restate the goal and the smallest change that meets it"]
    goal --> match{"A playbook fits?<br/>mf-playbooks list"}
    match -- yes --> show["mf-playbooks show {name}<br/>copy its steps into the todo list"]
    match -- "no, or large / unattended" --> figure["mf-feature-figure-it-out"]
    figure --> steps
    show --> steps["Work the steps"]
    steps --> route["Route by trigger to mf-feature-* skills"]
    steps --> principles["mf-principles show {name}<br/>for each principle applied"]
    steps --> delegate["Delegate to subagents<br/>kickoff line 1: Read {path}/worker.md"]
    route --> verify["Verify"]
    principles --> verify
    delegate --> review["Review each subagent's diff"] --> verify
    verify --> reply["Reply: goal first, principles cited,<br/>evidence or a label per claim"]
    reply --> pr["mf-playbooks show opening-a-pr"]
```

1. **Goal.** The first message restates the goal and the smallest change that meets it. Every subagent brief, PR `## Why` and final report opens with the same goal.
2. **Playbook.** The agent matches the task to a playbook and copies its steps into the todo list. No fit, or large, cross-cutting or unattended work, goes to `mf-feature-figure-it-out`.
3. **Work.** The agent follows the steps. It routes parts to skills, reads principles before applying them, and delegates.
4. **Verify.** The agent runs the checks itself. It never hands the human a check it could run.
5. **Reply.** Short declarative sentences. Each claim carries evidence or a label: measured, inferred, or guess.
6. **Open a PR.** `opening-a-pr` is invoked at the end of every other playbook.

## Routing

The entry skill maps triggers to skills. The agent loads a skill when its trigger appears in the work.

| Trigger | Skill |
| --- | --- |
| Code across a function boundary | `mf-feature-architect` |
| Fan-out work | `mf-feature-swarm` |
| A bakeoff between approaches | `mf-feature-arena` |
| A contested design | `mf-feature-interrogate` |
| Any prose, the reply included | `mf-feature-unslop` |
| Docs, PR descriptions, commit messages | `mf-feature-technical-writing` |
| Before review | `mf-feature-no-comments` |
| A number you measured | `mf-feature-benchmark-checklist` |
| Long or unattended work | `mf-feature-show-me-your-work` |
| No playbook fits | `mf-feature-figure-it-out` |

Before any code, the agent names the data shape. A fork it could settle by running something gets a prototype (`mf-playbooks show prototype`), not a question.

## Principles

The entry skill lists every principle under five headings: Core, Architecture, Verification, Delegation and Meta. Each entry says when it applies, for example "Laziness Protocol. Refactoring, sizing a diff, or tempted to add abstractions".

The rules for using one:

1. Find it in the index, or with `mf-principles list`. The name is the title in kebab case: `laziness-protocol`.
2. Read it in full with `mf-principles show laziness-protocol` before applying it.
3. In the reply, name the principle and the specific choice it changed.
4. Cite only principles read in this session.

## Playbooks

A playbook is a step list for one kind of task: `investigation`, `bug-fix`, `perf-issue`, `feature`, `refactoring`, `prototype`, `babysit`, `shipping`, `autonomous-run`, `session-pickup`, `opening-a-pr` and others. `mf-playbooks list` prints each with what it is for.

Each `PLAYBOOK.md` starts with frontmatter that names what it uses:

```yaml
---
name: feature
description: "New or changed behavior, built from a named data shape."
skills:
  - mf-feature-architect
  - mf-feature-arena
  - mf-feature-interrogate
principles:
  - model-the-domain
  - sequence-verifiable-units
  - separate-before-serializing-shared-state
playbooks:
  - opening-a-pr
---
```

The agent copies the numbered steps into its todo list and works them in order. `mf-playbooks verify` checks that every name in the frontmatter exists in the workspace.

## Subagents

The chat that receives `/mf-feature` runs the playbook and owns every subagent's work.

- **Kickoff.** The first line of every kickoff is `Read <path>/worker.md before anything else.`, with `<path>` the absolute folder of the `mf-feature` skill. The rest is the goal and the task.
- **Worker brief.** `worker.md` holds the rules a subagent needs: the kickoff's bar is the whole bar, never call a tool that asks a person a question, make any reversible choice and say why, stop only for deploys, deleted data, force-pushes or outside messages, and the PR title and body format.
- **Fresh by default.** A fix round, retry or follow-up goes to a new subagent with the original brief and the prior report. Resume one only when its state is costly to move.
- **Review.** The lead reviews each diff and writes its own summary.
- **Profiles and roles.** Delegated work runs as the `mf-feature-generic-worker` profile, on the harness and model that `mf-feature roles resolve <role>` returns. See [Agents and roles](#agents-and-roles).
- **Harnesses.** The text names concepts (spawn a subagent, ask a structured question, keep a todo list, loop until a check passes). [`references/harnesses.md`](../.agents/skills/mf-feature/references/harnesses.md) maps each concept to Claude Code, Codex, OpenCode, Pi and Cursor, and says what to do when a harness lacks it.

## Agents and roles

pstack answers two separate questions when a playbook step spawns a subagent. montflow keeps them separate.

| Question | pstack | montflow | Where it lives |
| --- | --- | --- | --- |
| **Who** is the subagent: how it behaves, what it reads first | an *agent* (`poteto-agent`, `comment-sicko`) | a *profile* | `.agents/@montflow/profiles/<name>/PROFILE.md`, shipped and installed by `mf-profiles doctor` |
| **Which harness and model** run it | a *role* (`bug-fix`, `swarm workers`, …) in a per-user Cursor rule written by `/setup-pstack` | a *role* in a per-user roles file | `.agents/@montflow/feature/roles.json`, git-ignored, managed by `mf-feature roles` |

So the Bug fix playbook's step 3 means: spawn the `mf-feature-generic-worker` profile on whatever the `bug-fix` role resolves to.

### Agents are profiles

| Profile | From pstack | What it does |
| --- | --- | --- |
| `mf-feature-generic-worker` | `poteto-agent` | The generic worker. Every playbook step that delegates code-writing or helper work spawns it. It reads the `mf-feature` skill and `worker.md` first, and reads each principle it applies with `mf-principles show`. |
| `mf-feature-comment-sicko` | `comment-sicko` | The comment reviewer `mf-feature-no-comments` spawns. It deletes every comment outside a short keep list and flags the code that needed a comment as `MUST KILL`. It never writes application code. |

The import writes both from pstack's agent files into `packages/mf-feature/profiles/`, and `mf-feature doctor` installs them. The body becomes `## Instructions`, and montflow adds a short `## Review Checklist` drawn from the agent's own rules. Neither pins a model: the role decides that.

A role is not a profile. A role holds no instructions, the same persona runs under almost every role, and its model choice is per user and per harness. Shipping roles as profiles would copy the generic worker's instructions into nine files, and `doctor` would overwrite a user's model choice on the next repair.

### Roles

There are nine roles:

| Role | Used for |
| --- | --- |
| `feature` | Feature and Refactoring playbooks |
| `bug-fix` | Bug fix playbook |
| `perf-issue` | Perf playbook |
| `hillclimb` | Hillclimb playbook |
| `judgment` | Prose and judgment calls |
| `swarm-workers` | Trivial mechanical edits, swarm workers, and every verification |
| `arena-runners` | `mf-feature-arena` candidates (a panel) |
| `arena-judges` | `mf-feature-arena`'s cross-judge (a panel the judge is picked from) |
| `interrogate-reviewers` | `mf-feature-interrogate` adversaries (a panel) |

A role is a list of **seats**. A single role has one seat, a panel has several. Each seat is an **ordered list of candidates**, and a candidate is a harness plus a model and an optional effort. The first candidate whose harness is available wins.

```jsonc
// .agents/@montflow/feature/roles.json (git-ignored, per user)
{
  "version": 1,
  "roles": {
    "bug-fix": [
      [
        { "harness": "claude-code", "model": "opus", "effort": "xhigh" },
        { "harness": "codex", "model": "gpt-5.5", "effort": "high" }
      ]
    ],
    "interrogate-reviewers": [
      [{ "harness": "claude-code", "model": "fable", "effort": "high" }],
      [
        { "harness": "codex", "model": "gpt-5.5", "effort": "high" },
        { "harness": "opencode", "model": "openai/gpt-5.5" }
      ],
      [{ "harness": "opencode", "model": "google/gemini-4-neon" }]
    ]
  }
}
```

A harness is **available** when it is the harness the session runs in, or when its CLI (`claude`, `codex`, `opencode`, `pi`) is installed. A seat that resolves to the current harness runs **natively**: the lead spawns it with its own subagent tool. A seat that resolves to another harness is **dispatched**: `mf-feature dispatch` runs it there headless (`claude -p`, `codex exec`, `opencode run`) and returns its report.

The lead never picks a harness itself. It asks the CLI, and does what each seat line's `next=` says:

```
$ mf-feature roles resolve interrogate-reviewers
role=interrogate-reviewers source=set current=claude-code seats=3
seat=1 run=native harness=claude-code model=fable effort=high next="spawn with your subagent tool on this model and effort"
seat=2 run=dispatch harness=codex model=gpt-5.5 effort=high next="mf-feature dispatch interrogate-reviewers --seat 2 --brief <file>"
seat=3 run=dropped skipped="pi:google/gemini-4-neon (pi not installed)" next="skip this seat and say so"
```

```mermaid
flowchart TD
    step["playbook step needs role R"] --> resolve["mf-feature roles resolve R"]
    resolve --> file{"R set in roles.json?"}
    file -- no --> def["defaults from the mf-feature Subagents section,<br/>on the current harness"]
    file -- yes --> seat["for each seat: first candidate<br/>whose harness is available"]
    seat --> none{"any candidate available?"}
    none -- no --> drop(["seat dropped and reported"])
    none -- yes --> where{"candidate harness = current?"}
    where -- yes --> native["native: spawn mf-feature-generic-worker<br/>with the subagent tool"]
    where -- no --> dispatch["dispatch: mf-feature dispatch<br/>runs it headless on that harness"]
    def --> native
```

- **Unset roles.** A role that is not in the file resolves to the defaults in the Subagents section of the `mf-feature` skill, on the current harness. Those defaults name no vendor or model id: the strongest model at high effort, one step lower for trivial edits, three vendors for a panel when the harness offers them.
- **Dropped seats.** A seat with no available candidate is dropped and reported. A panel keeps going with the seats it has (arena needs at least two runners).
- **Invalid combinations.** `mf-feature roles verify` checks every candidate against what its harness accepts. Claude Code takes `opus`, `sonnet`, `haiku` or `fable` plus an effort. Codex takes OpenAI models only, so `fable` under `codex` is an error. OpenCode takes `provider/model`. A bad combination fails before anything runs.
- **Setting roles.** `mf-feature roles set <role> --seat <spec>` writes the file, replacing pstack's `/setup-pstack`. A spec is the seat's candidates in preference order, `harness:model[:effort]`, comma-separated; repeat `--seat` for each seat of a panel. `mf-feature roles` shows what is set, in the same spec form, and `mf-feature roles unset <role>` goes back to the defaults.
- **OpenCode extra.** The OpenCode `model-fallback` plugin, which switches models on quota errors, can later read the same file to build its fallback chains. That stays OpenCode-only; the roles file does not depend on it.

### The mf-feature CLI

`packages/mf-feature` ships `mf-feature`. It owns every mechanical decision about roles, so the skill text only says "run this and do what it prints". It reads no store and ships no payload: the roles file is per user.

| Command | What it does |
| --- | --- |
| `mf-feature roles` (or `roles show`) | Every role: `<role>: default`, or its seats as specs, seats split by ` \| ` |
| `mf-feature roles set <role> --seat <spec>…` | Writes one role. Refuses, and writes nothing, when `verify` would fail |
| `mf-feature roles unset <role>` | Removes one role, so it resolves to the defaults |
| `mf-feature roles verify` | Checks the file. Non-zero on any error. No file is valid |
| `mf-feature roles resolve <role>` | One `key=value` line per seat, each ending in `next=` |
| `mf-feature dispatch <role> --seat <n> --brief <file>` | Runs a dispatch seat headless and prints its report |

How the CLI keeps agents from guessing:

- **It tells the harness itself.** `--harness` wins, then `MF_FEATURE_HARNESS`, then the environment markers Claude Code (`CLAUDECODE`), Codex (`CODEX_THREAD_ID`, `CODEX_SANDBOX*`) and OpenCode (`OPENCODE`) set for the commands they run. No marker, or markers from two harnesses, is a refusal that asks for `--harness`. It never guesses.
- **Every seat line names its next step.** `next=` is a spawn instruction, the exact `mf-feature dispatch` command, or "skip this seat and say so".
- **`dispatch` takes a role and a seat number, never a harness or model.** It resolves the seat itself, so a lead cannot dispatch to the wrong harness. It refuses a `native` or `dropped` seat and says what to do instead.
- **Nothing resolves from a bad file.** `resolve`, `show`, `set` and `dispatch` refuse a file with errors and point at `roles verify`.
- **The text cannot drift from the CLI.** The package's binary test scans every `mf-feature` skill, playbook, principle, profile, the harnesses reference and this page for `` `mf-feature <command>` ``, and fails on a command the binary does not have.

What `dispatch` runs, from the workspace root, with `MF_FEATURE_HARNESS=<harness>` set in the child so a lead nested inside it resolves correctly:

| Harness | Command | `--read-only` |
| --- | --- | --- |
| `claude-code` | `claude -p --model M [--effort E] --permission-mode auto`, brief on stdin | `--permission-mode plan` |
| `codex` | `codex exec --model M [--config model_reasoning_effort="E"] --sandbox workspace-write -`, brief on stdin | `--sandbox read-only` |
| `opencode` | `opencode run --model M[#E] --auto <brief>` | `--agent plan` |
| `pi` | `pi -p --model M [--thinking E] <brief>` | `--tools read,grep,find,ls` |

The brief is the profile's instructions (default `mf-feature-generic-worker`, `--profile none` for none), then the kickoff. `--dry-run` prints the command without running it. The Claude Code, Codex and OpenCode commands were run against their real CLIs; the Pi command follows its documented flags and has not been run.

`bun run mf-feature:check` runs `roles verify` on this checkout, and is part of `mf:check` and the CI matrix.

## The import

```mermaid
flowchart TD
    pin[".agents/@montflow/references/plugins/REFERENCE.md<br/>ref: {commit}"] --> sync["mf-references sync plugins"]
    sync --> clone[".agents/references/plugins/pstack<br/>git-ignored clone at the pinned commit"]
    clone --> script["scripts/import-mfstack.ts"]
    script --> s1["packages/mf-feature/skills/mf-feature{-name}/<br/>packages/mf-feature/profiles/mf-feature-*/<br/>packages/mf-feature/payload.json"]
    script --> s2["packages/mf-principles/principles/{name}/PRINCIPLE.md<br/>packages/mf-principles/payload.json"]
    script --> s3["packages/mf-playbooks/playbooks/{name}/PLAYBOOK.md<br/>packages/mf-playbooks/payload.json"]
    script --> lic["LICENSE-pstack in packages/mf-feature, the mf-feature skill,<br/>packages/mf-principles, packages/mf-playbooks"]
    s1 -- "mf-feature doctor" --> i1[".agents/skills/mf-feature*<br/>.agents/@montflow/profiles/mf-feature-*"]
    s2 -- "mf-principles doctor" --> i2[".agents/@montflow/principles/"]
    s3 -- "mf-playbooks doctor" --> i3[".agents/@montflow/playbooks/"]
    script -.->|"--check"| drift{"drift?"}
    drift -- yes --> fail(["exit 1: mfstack:check fails"])
    drift -- no --> ok(["exit 0"])
```

`bun run mfstack:import` runs `mf-references sync plugins`, the script, then each package's `generate:payload` (mode, profiles, principles, playbooks), so the embedded copies the compiled CLIs carry stay current. `bun run mfstack:check` runs the same with `--check`.

What the script does:

- **Refuses a moved clone.** The clone must sit at the `ref:` pinned in the registry entry.
- **Splits pstack three ways.** `principle-*` skills become principles. `poteto-mode/playbooks/*.md` become playbooks. Every other skill becomes `mf-feature-<name>`; `poteto-mode` becomes `mf-feature` and `poteto-help` becomes `mf-feature-help`. `setup-pstack` and `make-bot-ui` are skipped.
- **Renames in prose.** Skill names, slash commands and `pstack` become their `mf-` forms. Links to imported files point at their installed path; links to other pstack files point at the pinned commit on GitHub.
- **Writes frontmatter.** Skills get a stable `id` hashed from the name, `author: Lauren Tan`, the pstack version and `license: MIT`. Playbooks get a description from the pstack README table and the `skills`, `principles` and `playbooks` they mention.
- **Neutralizes harness terms.** Rules rewrite Cursor-specific wording into concepts: `.cursor/skills/` becomes `.agents/skills/`, the todolist tool becomes the todo list, `/loop` becomes your harness's loop, the role lines of `pstack-models.mdc` and configured model slugs become `mf-feature roles resolve <role>`, and Cursor's `create-skill` becomes `mf-create-skills`.
- **Applies hand edits.** Exact find-and-replace edits and whole-line rewrites (for the `mf-feature` Subagents section and the setup text of `mf-feature-help`) on top of the rename. Each must match exactly once, so an upstream rewording fails the import.
- **Turns agents into profiles.** `poteto-agent` becomes `mf-feature-generic-worker` and `comment-sicko` becomes `mf-feature-comment-sicko`, written to `packages/mf-feature/profiles/`.
- **Ships everything through the mode package.** Skills go to `packages/mf-feature/skills/`, and the import writes `packages/mf-feature/payload.json` listing every skill and profile. Upstream test suites (`scripts/test/`) are left out.
- **Adds montflow's own files.** `scripts/mfstack/harnesses.md` ships as `mf-feature/references/harnesses.md`.
- **Reports what is left.** It prints the harness-specific terms still in the text; the few left name Cursor on purpose, as an example.
- **Owns its directories.** A file in an imported directory that the import did not write is removed, or reported as `stale` under `--check`.

Drift is caught twice. `mfstack:check` compares the committed sources with a fresh import. `mf-principles:check` and `mf-playbooks:check` run `doctor --check`, which compares the installed stores with the packages. Both are in `mf:check` and in CI.

Never edit imported text by hand. Change the script, rerun the import, then run `bun run mf:doctor`.

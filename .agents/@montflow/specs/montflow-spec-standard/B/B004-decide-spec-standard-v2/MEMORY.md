### F0 — The v2 model in one table

| Concept | Source of truth | Stored? | Derivation |
| --- | --- | --- | --- |
| Phase exists | phase directory + `PHASE.md` | yes | directory name is the id |
| Phase objective / review decision / gate expectation | `PHASE.md` | yes | author prose; appraiser verdict |
| Phase status | task statuses | mirror in `PHASE.md` | derived; stale mirror is an error |
| Phase complete | task statuses | no | every task `complete` |
| Phase review passed | review store round **or** effective waiver | round: external; waiver: `PHASE.md` | `closed round` OR `review: waived` + complete + gate evidence |
| Phase locked | complete + gates proven + review passed | **no** | derived conjunction; never a list |
| Gate proof | `GATE-RESULTS.jsonl` | yes (generated) | `gate run` / `gate record` only |
| Task id | directory + `TASK.md` | yes | `<PHASE><NNN>`, numbering per phase |
| Spec contract version | `SPEC.md` `spec-version` | yes | absent reads as 1 |
| Broadcast / targeted message | `BOARD.md` / `MAILBOX.md` | yes, append-only | `mail` generator |
| Live binding | runtime claim registry | ephemeral, **not** a spec file | `claim` |

**The one invariant:** nothing a verifier checks is hand-typed by a worker or an
author. Every stored field has a designated writer: `create`/`init`/
`new-phase`/`new-task`/`migrate` scaffold it, `claim` writes every status
transition atomically under the orchestrator binding (and owns the runtime
binding), `gate run`/`gate record` own results, `mail` owns the channels, and
`stamp` owns instants. The execution orchestrator never hand-edits `TASK.md`,
the `SPEC.md` row, or the `PHASE.md` mirror: it proves its identity to `claim`
and `claim` writes all three in one transaction. `lock` writes nothing. A field
with no designated writer is a defect against B005/C001–C005, not an invitation
to hand-edit.

### F1 — `PHASE.md`: the phase record

Path: `<spec>/<PHASE>/PHASE.md`. One file per phase. It sits beside the task
directories B001 restored. The phase directory becomes:

```
<spec>/<PHASE>/
  PHASE.md            required at v2
  MEMORY.md           required at v2
  GATES.md            present iff PHASE.md `gate` is mechanical or subjective
  GATE-RESULTS.jsonl  generated by gate run / gate record; may be absent
  BOARD.md            permitted; required by the tier, never by check
  <PHASE><NNN>-<name>/  one or more task directories (B001)
```

Task directories gain exactly two allowed files: `MAILBOX.md` and
`GATE-RESULTS.jsonl`. They still require `TASK.md` + `MEMORY.md`; `GATES.md` stays
conditional on the spec table's `Gates` column.

#### Exact frontmatter

```markdown
---
id: B
objective: Decide the v2 standard contract.
status: complete
review: required
gate: none
---

# Phase B

## Notes

Optional prose.
```

A waived phase:

```markdown
---
id: A
objective: Rename the CLI flag and update its one test.
status: complete
review: waived
review-reason: One reversible flag rename proven by the package suite; no design judgment remains.
review-evidence: A001:0, A001:1
gate: none
---

# Phase A
```

| Field | Required | Type / values | Rule |
| --- | --- | --- | --- |
| `id` | always | `PHASE_PATTERN` (`^[A-Z]{1,2}$`) | must equal the directory name |
| `objective` | always | non-empty scalar | one line; no `<placeholder>` |
| `status` | always | `pending \| in-progress \| blocked \| complete` | must equal the derived status |
| `review` | always | `required \| waived` | the appraiser's per-phase decision |
| `review-reason` | iff `waived` | non-empty scalar | forbidden when `required` |
| `review-evidence` | iff `waived` | comma-separated result refs | forbidden when `required`; see F3 |
| `gate` | always | `mechanical \| subjective \| none` | the phase-level gate's kind |

**Body:** `<# Phase <id>>` is required and its id must equal `id`
(`phase.title-mismatch`). `## Notes` is optional; no other section is required.

**Derived status**, from the phase's parsed task statuses (phase-rank order):

```ts
export const derivePhaseStatus = (statuses: ReadonlyArray<TaskStatus>): PhaseStatus => {
  if (statuses.every((s) => s === 'complete')) return 'complete';
  if (statuses.some((s) => s === 'in-progress' || s === 'complete')) return 'in-progress';
  if (statuses.some((s) => s === 'blocked')) return 'blocked';
  return 'pending';
};
```

An empty task list is already a structure error; the status check is skipped when
any task in the phase failed to parse, so a broken task does not also produce a
stale-status error. `status` is a **conformity mirror**, not state: every reader
uses the derived status, and the verifier errors `phase.status-stale` when the
mirror disagrees.

**`gate` consistency:** the phase `GATES.md`, when present, must have at least
one stage and **every** stage must be classified with exactly the declared kind;
a phase-gate stage with no kind is `phase.gate-mismatch`. `validatePhaseGate(declared, stages)`
is the shared helper, used by both `check` and `migrate`. Task gates are
independent; a task may mix mechanical and subjective stages and retains the
legacy unclassified exemption (F5).

**Phase `MEMORY.md`:** the existing `modules/memory` contract (`# Memory` plus
`Context`, `Progress`, `Open Questions`, `Handoff`, `Deviations`). It is the
execution orchestrator's record for phase-scope decisions, review-budget
escalations, and cross-task handoffs. It is **not** a substitute for a task's
`MEMORY.md`.

**Phase `BOARD.md`:** optional by `check`. The tier file requires it for
`standard` and `full` and forbids it for `micro`; the verifier cannot see the
tier (B003 F2/F3), so absence is always structurally valid. A public test of
the authoring shape belongs to the phase review, not `check`.

**`PHASE.md` is not a lock list.** It carries the review *decision*, never a
`locked`/`locked-phases` field. Locking is still
`complete AND gates-proven AND review-passed` (F3).

### F2 — Task ids and directories: per-phase numbering, one sortable token

**Decision: keep `<PHASE><NNN>` and restart at `001` in every phase.**

- Task id: `^[A-Z]{1,2}\d{3}$` (`A001`, `B004`, `AA012`). The `TASK_ID_PATTERN`
  and `TASK_DIR_PATTERN` in `modules/task/task.module.ts:13,16` stay unchanged.
- Directory: `<spec>/<PHASE>/<TASK_ID>-<kebab-name>/`
  (`montflow-spec-standard/B/B004-decide-spec-standard-v2/`).
- `NNN` range `001`–`999`; `099` is now an ordinary number (no reservation).
  A phase with 999 tasks fails `new-task` with `task.id-exhausted`.
- New task number = `max(existing numeric suffix in that phase) + 1`, or `001`.
  `new-task` (C005) allocates from disk; no caller arithmetic.
- Within a spec, ids are unique by construction: `(phase, NNN)` is unique, and
  `check` already rejects duplicate ids. Across specs ids repeat by design and
  resolve in the spec's namespace (`depends-on`, `related-tasks`, `originator`).
- `new-phase` allocates the next phase id after the highest existing rank
  (`phaseRank`), never reusing a deleted id; `init` starts at `A`.

**Collision resolution (the explicit question).** There is no collision between
B001's phase directory `B/` and the id `B001` inside it:

1. the phase token is exactly `^[A-Z]{1,2}$`; the task token is
   `<letters><3 digits>`; the two patterns are disjoint, so a phase is never a
   task id and vice versa;
2. the path `B/B001-<name>/` deliberately repeats the phase prefix; the existing
   structure check (`structure.module.ts:361-368`) already requires the prefix to
   agree with the containing directory;
3. at the spec root, `B` is a phase and `B001-...` is a misplaced task directory
   (`structure.module.ts:266-277`); neither can be read as the other.

The repetition is the point: the id is globally unique inside the spec and the
path stays readable without a lookup.

**Sort key.** The raw id is not lexicographically sortable across one- and
two-letter phases (`AA001 < B001` in a string sort, but phase `AA` is rank 27).
Every ordering uses one arithmetic token:

```ts
sortKey(id) = phaseRank(phaseOf(id)) * 1000 + Number(id.slice(phaseOf(id).length))
// A002 = 1002, B001 = 2001, AA001 = 27001 → A002, B001, AA001
```

`phaseRank` already exists in `modules/task/task.module.ts:192`; `structure`,
`lifecycle`, `review-link`, and `migrate` already use it. Add one test that fixes
the order `A002 < B001 < AA001` so no future surface reintroduces a string sort.

**Review tasks are ordinary tasks.** They are numbered normally (`A003`, not
`A099`), named `review-phase`, typed `review`, and carry `reviewer-profiles`.
`modules/scaffold` must drop `REVIEW_NUMBER = 99`, the unconditional append, and
the `reviewId` result field; `create --tasks` must accept `type: review` so the
creation orchestrator can request one when the tier requires it. Historical
`*099-review-phase` records remain valid ordinary ids.

### F3 — Derived locks and the review-waiver record

**B001's rule is confirmed and extended, not replaced:**

```
phaseComplete(p)   := every task under p is complete
gatesProven(p)     := every classified mechanical stage in p and in p's tasks
                      has a latest recorded pass (vacuously true at v1)
reviewPassed(p)    := hasClosedRoundAttributedTo(p) OR effectiveWaiver(p)
locked(p)          := phaseComplete(p) AND gatesProven(p) AND reviewPassed(p)
```

- `hasClosedRoundAttributedTo(p)` is exactly B001's
  `ReviewLink.passedPhases`: a round with `- Phase: <p>` in `## Metadata` and
  `- Status: closed`, in any expected series (`review-link.module.ts:105-135`).
- `gatesProven` is the "gate recorded" conjunct of this task's brief. It is new
  only where the new gate kinds exist: a v1 phase has no classified stage, so it
  is vacuously true and B001's behavior is unchanged. A complete phase with a
  failed/unrecorded mechanical stage stays unlocked *and* `check` reports
  `gate.unproven`, so `state` and `check` cannot disagree.
- `effectiveWaiver(p)` is the new half, defined below. It already implies
  `gatesProven` (every stage must pass), so on the waiver path the conjunct is
  redundant; on the review-round path it is the missing gate proof.
- There is no stored lock list, no lock field, and no writer of a lock. The
  conjunction makes "locked but incomplete", "locked with an unproven gate", and
  "locked without a review decision" impossible, so no lock contradiction state
  can exist.

**Where the waiver is recorded — one place, no new file:**

`<spec>/<PHASE>/PHASE.md` frontmatter:

| Field | Value |
| --- | --- |
| `review` | `waived` |
| `review-reason` | one line: why the phase's gates stand in for a review round |
| `review-evidence` | comma-separated refs to the gate results that prove it |

The phase is named by `id` (equal to the directory). There is **no** `WAIVER.md`,
no `locked-phases` line, and no second copy of the decision. This is the field
B003's `micro` default depends on.

**Evidence ref grammar:**

```
ref   := "phase:" stage | task-id ":" stage
stage := 0 | [1-9][0-9]*
```

Examples: `phase:0`, `A001:1`, `B002:0`. Comma-separated, whitespace trimmed, no
duplicates, no refs to another phase's tasks.

**When a waiver is *declared* vs *effective*:**

- **Declared** at authoring: `review: waived` + a valid reason. The creation
  orchestrator writes it from the appraiser's verdict; the execution
  orchestrator never converts a `required` phase to `waived`. The evidence refs
  are written at authoring from the stages it just authored.
- **Effective** only when all of these hold:
  1. `review === 'waived'` and `review-reason` is valid;
  2. the phase is complete (every task `complete`);
  3. every task in the phase has `GATES.md` with at least one stage (the
     **fully-gated** definition);
  4. every stage in the phase `GATES.md` (if any) and in every task `GATES.md`
     is classified (`mechanical` or `subjective`) and has a latest passing
     result (F5);
  5. `review-evidence` is non-empty and its ref set **equals** the set of all
     those stages — no missing stage, no extra ref, no unresolved ref.
- Findings 3–5 are reported **only when the phase is complete**. While work is
  open, an empty evidence list is legal: the refs exist, the results do not yet.
  This is what lets a `micro` phase be authored before its gates run.
- A malformed ref is always `phase.evidence-invalid`; a ref to a stage outside
  the phase is always `phase.evidence-invalid`.
- The tier's waiver policy is part of the precondition: `full` never waives, and
  a `standard` phase is `records-only`, meaning every task in it is
  `planning`/`exploratory`/`review` (no code or record work). `effectiveWaiver`
  re-applies that predicate on every read, so a waived phase with an
  `execution`/`defect`/`interruptor` task is not effective and stays unlocked
  (B003 F3). `micro`'s waiver is `permitted` subject only to conditions 1–5 and
  is **exempt from the `records-only` predicate**; an auth/data `micro` phase
  may be upgraded to `required` but a waiver is never forced. The default
  `micro` tree (one execution task, review waived) therefore locks once the task
  closes and its gate is proven.
- `review: waived` **with a `review`-type task** is an error
  (`phase.waiver-with-review-task`): a phase either reviews or waives.
- `review: required` with no review task is a warning
  (`phase.review-task-missing`); the phase stays unlocked, which is honest and
  matches B001's "no phase requires one".

**Wiring.** `lifecycle.Input` gains two required fields beside `reviewedPhases`:
`waivedPhases` and `provenPhases` (both `ReadonlyArray<string>`).
`phaseSummaries` becomes
`locked = complete === total && proven.has(p) && (reviewed.has(p) || waived.has(p))`
(`lifecycle.module.ts:77-90`). `structure.verifySpecTree` passes
`passedPhases(review.series)` plus the two sets from `phaseEvidence(snapshot)`.
The same helper feeds `cli.status.summarize`
(`cli.status.module.ts:112-116`) and
`apps/workspace/src/services/specs/specs.services.module.ts:299-302`.

Public helper:

```ts
// modules/structure (or modules/phase; one implementation, re-exported)
export const phaseEvidence = (
  snapshot: SpecSnapshot,
): {
  readonly waived: ReadonlyArray<string>;   // effective waivers
  readonly proven: ReadonlyArray<string>;   // complete gate proof for the phase's mechanical stages
  readonly issues: ReadonlyArray<Issue>;
};
```

It parses `PHASE.md`, task `GATES.md`, and `GATE-RESULTS.jsonl`; returns the
effective waiver set, the proven set, and every phase/gate code. `check` (which
passes `NO_REVIEW`) can then lock a waived `micro` phase with no review store at
all.

### F4 — The no-review case, end to end

A small, fully gated phase ships without a review task:

1. The appraiser's verdict says `waived` with a one-clause reason (field 3 of
   `.agents/@montflow/profiles/spec-appraiser/PROFILE.md:39-40`).
2. The creation orchestrator writes `PHASE.md` with `review: waived`,
   `review-reason`, and `review-evidence` naming every stage it authored. It
   writes **no** `review` task.
3. `gate run` records each mechanical stage; a reviewer role records each
   subjective stage (F5). Results land in the task's and/or phase's
   `GATE-RESULTS.jsonl`.
4. When every task is complete, `effectiveWaiver` becomes true and every stage is
   proven (F3), so `locked = complete AND proven AND true` and the phase locks.
   If a result is missing, the phase stays unlocked and `check` names the unproven
   stage.

Consequences:

- **`mf-specs state` and `check` agree without a review store.** The waiver is
  local to the spec tree.
- **No waiver = no lock.** A `micro` phase is authorable because the waiver
  record exists; B003's dependency is satisfied.
- **The execution orchestrator cannot waive its way to a lock.** Only the
  creation orchestrator writes the decision, from the appraiser's verdict.
- **Migration never invents a waiver** (F7): a migrated phase without a review
  task is `review: required` and stays unlocked until its owner adds the task or
  re-authors the decision.

### F5 — Gate stage kinds and the recorded result

**The recognizable `GATES.md` shape stays.** A stage is still a `##` heading with
checkbox items. The kind is declared on the heading; metadata lives on the lines
between the heading and the first item.

```markdown
## Stage 1: Typecheck (mechanical)
command: bun run ts:check

- [x] `tsc --noEmit` exits 0.

## Stage 2: Review the error channel (subjective)
judge: effect-reviewer

- [x] Every failure is a tagged error; no string throws.
```

Exact grammar:

- Heading: `^##\s+Stage\s+(\d+):\s+(.+?)\s*\((mechanical|subjective)\)\s*$`.
  The number is a decimal integer, unique per file; the title is non-empty.
- **Unclassified** heading (`## Stage 1: …`, no suffix) is a legacy stage **only
  in a task `GATES.md`** — the v1 compatibility rule. There it parses exactly as
  today, is never runnable, requires no result, and produces no new finding.
  This is why old task `GATES.md` files verify unchanged (C002). A phase
  `GATES.md` is v2-only and gets no exemption: a phase-gate stage with no kind is
  `phase.gate-mismatch`, the same code `check` reports and `migrate` refuses on
  (F7).
- `command:` exactly once on a mechanical stage; `judge:` exactly once on a
  subjective stage; each is forbidden on the other kind. Either line on an
  unclassified stage is `gate.kind-missing`.
- `command:` is the literal shell command (one surrounding pair of backticks is
  stripped if present); it must not contain `<…>`. `judge:` is a profile slug
  (`SLUG_PATTERN`); the verifier checks the slug shape, not that the profile
  exists (profiles live outside the spec store).
- The existing shape rules stay: non-empty file, at least one `## Stage`, at
  least one item per stage, no empty item, no `<placeholder>` item.
- `gate run` executes from the **workspace root** (the parent of
  `.agents/@montflow/specs`, the same root `which`/`author` resolve). It never
  edits `GATES.md`.

New gate codes: `gate.kind-missing`, `gate.malformed-metadata`,
`gate.duplicate-stage`, `gate.placeholder-command`, `gate.unproven` (error),
`gate.unjudged` (warning), `gate.result-inconsistent`, `gate.results-malformed`,
`gate.result-owner-mismatch`. Existing `gate.unchecked` stays.

#### Recorded result: path and exact line shape

**Path:**

- task: `<spec>/<PHASE>/<TASK>/GATE-RESULTS.jsonl`
- phase: `<spec>/<PHASE>/GATE-RESULTS.jsonl`

**Format:** JSON Lines, append-only, one record per stage run. The generator
(`gate run` / `gate record`) uses `JSON.stringify`, so the verbatim output is
escaped and every record is one physical line. A blank line is ignored; any other
unparsable line is `gate.results-malformed` with the line number.

**Mechanical record (exact keys, no extras):**

```json
{"stage":1,"title":"Typecheck","kind":"mechanical","command":"bun run ts:check","exit":0,"verdict":"pass","at":"2026-11-02T21:40:00Z","output":"$ tsc --noEmit\n"}
```

**Subjective record:**

```json
{"stage":2,"title":"Review the error channel","kind":"subjective","judge":"effect-reviewer","verdict":"pass","at":"2026-11-02T21:42:00Z","note":"Every failure is a tagged error; no string throws."}
```

| Key | Mechanical | Subjective | Rule |
| --- | --- | --- | --- |
| `stage` | required | required | integer ≥ 0, must name a stage in the owner's `GATES.md` |
| `title` | required | required | informational; not compared |
| `kind` | `"mechanical"` | `"subjective"` | must equal the stage's kind |
| `command` | required | forbidden | must equal the stage's `command:` (trimmed) |
| `judge` | forbidden | required | profile slug; the role that judged |
| `exit` | required | forbidden | integer 0–255 |
| `verdict` | required | required | exactly `pass` or `fail` |
| `at` | required | required | `YYYY-MM-DDTHH:MM:SSZ`, from the CLI clock or `stamp` |
| `output` | required | forbidden | combined stdout+stderr, verbatim |
| `note` | forbidden | required | the judge's reason |

**Rules:**

- `verdict` is the generator's consistency check: `pass` iff `exit === 0`;
  otherwise `gate.result-inconsistent` (error). A subjective `verdict` comes from
  the reviewer role and carries no exit.
- The **last line in file order** for a stage is authoritative. A later `fail`
  after an earlier `pass` unproves the stage. A changed `command:` invalidates
  every old record (the last record's command no longer matches) → the stage is
  unproven. A changed title does not.
- A record whose `stage` is absent from `GATES.md` is
  `gate.result-owner-mismatch` (error), even on an unfinished owner: fabricated
  evidence is never silent.
- **Completion rule:** a `complete` task/phase with a `mechanical` stage must have
  a latest `pass` for it (`gate.unproven` error). A `complete` owner with a
  `subjective` stage and no `pass` is `gate.unjudged` (warning). An unfinished
  owner gets no unproven/unjudged finding.
- **Gate progress** (`verifyGateProgress`) is satisfied when the owner is not
  complete, **or** at least one item is checked, **or** at least one stage has a
  recorded `pass`. Old all-unchecked complete gates still fail `gate.unchecked`
  (no results exist); a completed v2 gate with a passing result no longer needs a
  ticked box to prove itself.
- **Subjective stages are never auto-passed.** Only `gate record` writes them,
  after the reviewer role named in `judge:` returns a verdict; the record names
  the judge. `gate run` refuses a subjective stage (`gate.not-mechanical`);
  `gate record` refuses a mechanical stage (`gate.not-subjective`).
- **Phase gate and B003 `full`:** the phase `GATES.md` mechanical stage is the
  "one mechanical run of the suite" B003 F3 requires before a review round. The

### F6 — `SPEC.md` `spec-version`: values, constant, codes

One field, one constant, four codes, all in `modules/spec/spec.module.ts`:

```ts
export const SPEC_VERSION_FIELD = 'spec-version';
export const SPEC_STANDARD_VERSION = 2;          // current
export const SPEC_STANDARD_PREVIOUS = 1;         // accepted, warned
export const SPEC_STANDARD_VERSIONS = [1, 2] as const;
export const SPEC_VERSION_CODES = {
  invalid: 'spec.version-invalid',
  outdated: 'spec.version-outdated',
  future: 'spec.version-future',
  untransformed: 'spec.version-untransformed',
} as const;
```

`readSpecVersion(fields)` returns `{ version, declared, issues }`; `verifySpecFile`
pushes the issues; `verifySpecTree` reads it again for the transformation check.
The field is **not** added to the `Spec` Schema.Class, so an invalid value cannot
delete the whole descriptor from every consumer.

| Declared | Read as | Finding |
| --- | --- | --- |
| absent | 1 | `spec.version-outdated` (warning) |
| `1` | 1 | `spec.version-outdated` (warning) |
| `2` | 2 | none |
| integer `> 2` | as written | `spec.version-future` (error) |
| non-decimal, `0`, negative | 1 (fallback) | `spec.version-invalid` (error) |

- **Why absent warns:** the task and C001 both require "absent reads as the
  previous standard and warns". A v1 record is accepted, never stranded.
- **Why 0 is invalid, not "below":** there is no v0 standard; a typo must not pass
  as a warning. "Below current" means the real previous standard.
- **Diagnostic text:** outdated → `Spec declares standard version 1; the current
  standard is 2.` expected `spec-version: 2`, actual `1`, fix
  `Run mf-specs migrate --name <spec>, or leave it as a frozen v1 record.`
  future → `Spec declares standard version <n>, above the supported 2.` fix
  `Set spec-version to 2, or upgrade mf-specs.`
- New specs (`create`/`init`) write `spec-version: 2` from day one. Only
  `migrate` writes it onto an existing record.

### F7 — `migrate`: two legacy shapes, one v2 shape, one rejection

**Inputs and plans** (`cli.migrate.module.ts`, `MigrationPlan` gains
`writes` and `upgrade`):

| Snapshot shape | `spec-version` | Plan |
| --- | --- | --- |
| task dirs at root, no phase dirs | absent/1 | `migrate`: B001's moves, then the upgrade writes |
| `<PHASE>/<task>/`, no `PHASE.md` | absent/1 | `upgrade`: writes |
| `<PHASE>/<task>/`, some `PHASE.md` | absent/1/2 | `upgrade`: fills the missing files, ensures 2 |
| complete v2 tree | 2 | `already`: verify only |
| `status: complete` | any | `frozen`: skip unless `--include-complete` |
| `spec-version > 2` | — | `refused` (`spec.version-future`); never downgrade |
| invalid `spec-version` | — | `refused` (`spec.version-invalid`) |
| mixed flat + phase dirs | any | `refused` (existing reason) |

**Order of the checks:** a `status: complete` spec is evaluated for `frozen`
first (so a complete v2 tree also reports `frozen`, not `already`, unless
`--include-complete` is passed); an invalid or future version refuses before any
planning; then the shape selects `already`/`upgrade`/`migrate`.

`MigrateSpecResult.status` is `migrated` for a flat→phase move, `upgraded` for a
phase-tree write pass, `frozen` for a skipped complete spec, plus the existing
`already|planned|refused|failed`; `writes` is a `ReadonlyArray<string>` of paths
for the report (`would write` under `--dry-run`, `wrote` otherwise).
`migrateFailed` includes `refused|failed`, not `frozen`.

**The transformation, exactly.** The tree predicate is **version-independent**;
the version check is applied on top of it.

```ts
export const isV2Transformed = (snapshot: SpecSnapshot): { ok: boolean; reason?: string }
```

It is true iff all hold:

1. every phase directory contains `PHASE.md` whose `id` equals the directory;
2. no task directory exists at the spec root;
3. every file in a phase directory is in the v2 phase allowlist, and every file
   in a task directory is in the task allowlist.

`verifySpecTree` emits `spec.version-untransformed` (error) when
`readSpecVersion(fields).version >= 2` **and** `isV2Transformed` fails, naming the
first failing reason (e.g. `phase 'A' has no PHASE.md`). This is the "version bump
without transformation is rejected" rule: a record cannot relabel itself v2 while
keeping the v1 tree. A v3 tree that *is* transformed gets only
`spec.version-future`. The existing layout findings still fire independently; the
version code is the specific signal.

**The upgrade writes** (per phase, in phase-rank order):

- `<PHASE>/PHASE.md`:
  - `id`: the directory name;
  - `objective`: `TODO: state what phase <id> must achieve.` (migration cannot
    invent prose; the owner replaces it, the same way `create` writes
    `TODO: describe this task.`);
  - `status`: `derivePhaseStatus` over the phase's tasks;
  - `review`: **`required`** always (migration never invents a waiver);
  - no `review-reason`, no `review-evidence`;
  - `gate`: `none` when there is no phase `GATES.md`; when one exists,
    `mechanical`/`subjective` if every classified stage agrees, otherwise the
    plan is `refused` and asks for a manual decision (mixed or unclassified
    phase gate);
  - body `# Phase <id>` and a `## Notes` line recording the migration.
- `<PHASE>/MEMORY.md`: the standard `modules/memory` template, only if absent.
- `SPEC.md`: add/replace exactly one frontmatter line, `spec-version: 2`,
  inserted immediately before the closing `---`. Every other byte, the body, and
  the trailing newline are preserved. **This is the one file edit migrate makes,
  and it happens last**, after every `PHASE.md` exists, so a version bump can
  never precede its transformation.

**Order and rollback:** plan → moves (flat only) → verify the moved snapshot →
writes → verify the v2 snapshot. On any failure, restore the original `SPEC.md`
bytes and delete only the files this run created (pre-existing `PHASE.md`/
`MEMORY.md` are left alone), then reverse the moves. A pre-existing `PHASE.md`
is validated as-is, never repaired field-by-field: an invalid or incomplete one
fails the post-write verify and the run rolls back with its findings, so owner
prose is never silently overwritten. `SpecStore` needs
`removeFile(root, name, path)` alongside `move`/`removeDirectory`; restoring
`SPEC.md` uses the existing `write` with the original content. A second run is
`already` and verifies; it never rewrites.

**What migrate does not do:** it does not run gates, does not write results, does
not add a review task, does not waive, and does not touch a frozen complete spec
without `--include-complete`.

### F8 — `BOARD.md` broadcast and `MAILBOX.md` targeted grammar

**Files:**

- `<spec>/<PHASE>/BOARD.md` — phase broadcast, `to all`.
- `<spec>/<PHASE>/<TASK>/MAILBOX.md` — one task's targeted mail.

Both are append-only, plain markdown, no frontmatter. A board is per phase; there
is no spec-root board (the root allowlist stays `SPEC.md` + `sizing.json` + phase
dirs).

**Exact shape:**

```markdown
# Board

## 2026-11-02T21:15:00Z · from B004 · to all

The gate runner is now `mf-specs gate run`; run it before marking a task complete.
```

```markdown
# Mailbox

## 2026-11-02T21:22:00Z · from B004 · to C001

Question: should the v1 fixture keep `locked-phases`? Answer: no; strip it.
```

**Entry heading grammar** (one regex for both kinds):

```
^##\s+(\d{4}-(0[1-9]|1[0-2])-(0[1-9]|[12]\d|3[01])T([01]\d|2[0-3]):[0-5]\d:[0-5]\dZ)\s+·\s+from\s+([A-Z]{1,2}\d{3}|orchestrator)\s+·\s+to\s+(all|[A-Z]{1,2}\d{3})\s*$
```

- The separator is U+00B7 MIDDLE DOT with single spaces: ` · `.
- The timestamp is UTC, second precision, `…Z`; the regex month/day/hour ranges
  are checked. `mf-specs stamp` prints exactly this format; `mail` uses it
  internally, so no agent types one.
- `from` is a task id that exists in this spec, or the literal `orchestrator`.
- `to` is `all` (board only) or a task id (mailbox only).
- The first non-blank line is `# Board` or `# Mailbox`; content between that
  title and the first entry other than blank lines is `*.stray-content`.
- Each entry body is every line after the heading until the next `^## ` line;
  it must contain at least one non-blank line. It may contain `#`, `###`, code
  fences, and tables; it may not contain a level-2 `## ` heading (that starts the
  next entry). The generator renders `## <ts> · from <id> · to <target>`, a blank
  line, the body, and a blank line.

**Verifier parse rules (exact):**

| Rule | Finding |
| --- | --- |
| title missing/wrong | `board.malformed-title` / `mail.malformed-title` |
| a `## ` line not matching the heading regex | `board.malformed-entry` / `mail.malformed-entry`, with `line` and `field: "<file>:<line>"` |
| empty body | `board.empty-entry` / `mail.empty-entry` |
| timestamp earlier than the previous entry | `board.out-of-order` / `mail.out-of-order` |
| board `to` ≠ `all` | `board.target-invalid` |
| board `from` not a known id/`orchestrator` | `board.unknown-author` |
| mailbox `from` not a known id/`orchestrator` | `mail.unknown-sender` || mailbox `to` not a known task id | `mail.unknown-recipient` |
| mailbox `to` ≠ the mailbox owner's id | `mail.recipient-mismatch` |
| mailbox `from` = `to` | `mail.self-addressed` |
| content between the title and the first entry | `*.stray-content` |

"Append-only" is a writer invariant; the verifier's mechanical proxy is
non-decreasing timestamps plus the title/entry grammar. It cannot detect a
rewritten body or a deleted old entry; the generator never rewrites, and the
review may diff the file.

**Writer and delivery path.** One verb, `mail` (C006 adds it to the execution
prompt and the docs; B005 fixes the flags):

```
mf-specs mail --to <task-id|all> [--phase <id>] --text <text> [--session <session-id>]
```

The sender is **not a flag**: it is derived from the caller's claim binding, and
only a session holding the spec's orchestrator binding may call `mail` (B005
F1). Every entry is authored by `orchestrator`; a worker cannot send as another
task or as the orchestrator because it cannot supply a sender at all.

1. Resolve the recipient: `all` → the caller's/`--phase` board; a task id → that
   task's `MAILBOX.md`. Validate the addressee **before** writing.
2. Append the entry in one write (durable first). A malformed existing file is
   refused, never repaired by appending.
3. For a task target with a live claim binding: render the same entry text and
   call the injected `SessionSteerPort.steer(sessionId, text)`. Success → exit 0,
   `delivered live <session>`. Failure → the entry remains, exit 0 with a
   `mail.steer-failed` **warning** and `queued`; a message never disappears
   because steering failed.
4. No binding → exit 0, `queued`. The worker reads its `MAILBOX.md` at start and
   before its receipt (spec-worker steps 1 and 5), so the file is the fallback
   delivery path.
5. `all` is never steered; every worker reads the phase `BOARD.md` at start.

The claim binding is **not** a spec file:

```ts
interface Claim {
  spec: string;
  task: string; // a task id, or the sentinel 'orchestrator'
  session: string;
  at: string; // ISO instant
}
```

`claim` (C005) **writes the status records atomically** when it is called under
the orchestrator binding: a transitioning form (`--start`, `--block`, `--close`,
or an orchestrator `--release`) rewrites the task `status:` in `TASK.md`, the
matching `SPEC.md` `## Tasks` row, and the `PHASE.md` status mirror in one
transaction. The graph is complete: `--start` is `pending → in-progress`,
`--block` is `pending | in-progress → blocked`, an orchestrator `--release` is
`blocked | in-progress → pending`, and `--close` is `in-progress → complete`; a
blocked task returns through `--release` then `--start`, never a hand edit. A
bind or a worker's own `--release` writes only the registry
entry. The registry stays runtime-only at
`.agents/@montflow/.runtime/claims.json` (one workspace path, agreed with B005),
no verifier reads it, and `lifecycle`'s `active` flag may use it. This is what
`mail` and the restricted forms (`claim --start`, `claim --block`,
`claim --close`, `gate run`, `mail`) look up; a stale/absent binding means
`queued` or `not-orchestrator`.

**Dependency rule:** a channel never substitutes for `depends-on`. A mid-flight
sibling need is a dependency edge, not a mailbox thread; the execution skill and
the phase review state it.

### F9 — The single-writer rule

**One orchestrator per spec writes state; everything else is generated.**

| Record / field | Writer | Mechanism |
| --- | --- | --- |
| `SPEC.md` `name`/`author`/`created`/`workspace-type` | creation orchestrator | `init`/`create` |
| `SPEC.md` `spec-version` | `migrate`/`init` only | generator; **never hand-typed** |
| `SPEC.md` `## Creation` (`tier`, `questions n/budget`, `unresolved`) | `init` writes; the creation orchestrator updates the count | `init` / edit |
| `SPEC.md` `status` | `claim` under the orchestrator binding | generator; atomic with the task and phase statuses; `lock` only confirms, writes nothing |
| `SPEC.md` `## Tasks` rows | `new-task`/`init`/`create` add/drop rows; `claim` writes the row's status | generator; no hand edit |
| `SPEC.md` prose | creation orchestrator | edit |
| `PHASE.md` `objective` | creation orchestrator | `new-phase` or prose edit |
| `PHASE.md` `review`/`review-reason`/`review-evidence` | creation orchestrator, from the appraiser verdict | `new-phase`/`init`/prose |
| `PHASE.md` `status` | `claim` under the orchestrator binding | generator; atomic with the other two status records |
| `PHASE.md` `gate` | creation orchestrator, from the appraiser verdict | `new-phase`/`init` |
| phase `MEMORY.md` | execution orchestrator | edit |
| `TASK.md` id/name/dir/status scaffold | `new-task`/`create` | generator (writes `pending` only) |
| `TASK.md` `status` | `claim` under the orchestrator binding | generator; atomic with the `SPEC.md` row and `PHASE.md` mirror |
| `TASK.md` prose/`size`/`depends-on` | creation orchestrator / author | edit |
| task `MEMORY.md` | **that task's worker** | edit; the only file a worker owns |
| `GATES.md` | author (prose); the worker fills placeholders before running | edit |
| `GATE-RESULTS.jsonl` | `gate run` / `gate record` only | generator; no agent edit |
| `BOARD.md` / `MAILBOX.md` | `mail` only | append; no agent edit |
| `.agents/@montflow/.runtime/claims.json` | `claim` only | runtime binding; never a spec file |
| review round (`REVIEW.md`, `- Status:`) | `mf-reviews` extension only | never the orchestrator |
| locks | **nobody** | derived |
| timestamps | `stamp` | never typed |

**The appraiser writes nothing** (`spec-appraiser` profile: zero writes). It only
returns the tier, phase plan, per-phase review decision, gate kind, parallelism,
evidence. The creation orchestrator records those fields.

**The bookkeeper** repairs records through the owning skill; it never writes
status, locks, or prose (its profile's "What you may not touch").

**The execution orchestrator** is the only agent that talks to the user and the
only caller of the status generator. The restricted verbs prove that identity
instead of assuming it: only a session holding the spec's `orchestrator` claim
binding may call `claim --start`, `claim --block`, `claim --close` (or
`claim --release` when it resets an `in-progress` or `blocked` task to
`pending`), `gate run`, or
`mail` (B005 F1). `claim` writes the task `status:`, the `SPEC.md` row, and the
`PHASE.md` mirror in one transaction and records or clears the binding; `gate
run` writes only `GATE-RESULTS.jsonl`; `mail` writes only the channel files.
`mf-specs lock <phase>` is a **confirmation** verb (B005/C005): it recomputes
`complete AND gates-proven AND review-passed`, exits non-zero when the phase is
not lockable, and writes nothing. It is not a lock list and it owns no status
row. This resolves the profile's `mf-specs lock` line against the current
prompt's "no lock verb": the verb exists after C005, but it can never store a
lock.

**Worker escalation (never `ask_user`):**

1. On a decision only the user can make, the worker writes one line under
   `## Open Questions` in its own `MEMORY.md`:
   `- Q: <one sentence> · blocks: <TASK.md item or step> · default: <the default it would take>`.
2. It does **not** call `ask_user`, does **not** write the orchestrator's records,
   and does **not** use a channel to replace a dependency.
3. It returns `failed` when the answer is required to finish, with the question
   and what it attempted; `done` when its scoped work is complete and the
   question is advisory.
4. The execution orchestrator reads the receipt + `MEMORY.md`, then either answers
   by appending to the task's `MAILBOX.md` and re-dispatching, or calls
   `ask_user` itself. The user is never asked by a worker.

### F10 — Existing v1 specs, and the frozen-complete rule

**Version 1 means:** the B001 phase tree (`<spec>/<PHASE>/<task>/`) without the
v2 phase artifacts. It is accepted with `spec.version-outdated` (warning).
`PHASE.md` and phase `MEMORY.md` are optional at v1 and required at v2. The flat
pre-B001 tree is **not** made valid by version 1: B001's layout rule is
orthogonal and stays an error, and `migrate` is the fix (`montflow-phase-directories`
deliberately removed the flat tolerance).

**When v2 lands:**

- Every `status: in-progress` spec is upgraded in the v2 wave by
  `mf-specs migrate --all`: `spec-version: 2`, `PHASE.md` + phase `MEMORY.md` in
  every phase, derived statuses, `review: required`, `gate: none` (no phase gate
  exists in any current tree). Owner prose (objectives) is a `TODO` placeholder
  the owner replaces; no gate and no task is rewritten.
- Every spec that is `status: complete` at the cut is **frozen**: `migrate` skips
  it (`frozen`), it keeps its phase tree and historical `099` tasks, and it is
  read as v1 forever unless someone deliberately runs
  `migrate --name <spec> --include-complete`. The frozen set is recorded by
  C007's artifact ledger (`C007` TASK: "recorded as frozen or upgraded").
- **Read rule:** every surface reads `spec-version` absent as 1, never infers v2
  from file presence, never requires `PHASE.md` at v1, and never offers a frozen
  spec for dispatch. `check` reports `spec.version-outdated` warnings for frozen
  specs and exits 0. `status`/`state`/`list` show them with derived locks from
  whatever closed rounds the review store holds (or none). No later task edits a
  frozen record: not its prose, its tree, its status, or its gates.
- A frozen spec can be upgraded only by an explicit `--include-complete` run;
  after that it is v2 and normal rules apply.

**This spec (`montflow-spec-standard`)** is `in-progress` at the cut, so it is
**upgraded**, not frozen. Its historical completed tasks are untouched; only its
tree gains `PHASE.md`.

   `--include-complete` upgrade. The alternative (upgrade every complete spec
   structurally, freezing only prose) is a one-flag change in C001/C005 and
   changes no file format. Recorded, not blocking.
2. **A waiver may cite subjective gate judgments, not just mechanical ones.**
   Default taken: yes, because `standard`'s `records-only` waiver covers phases
   with no runnable artifact, and the judgment is named (`judge:`) and recorded by
   the reviewer role, not invented. If the user wants mechanical-only waiver
   evidence, the check tightens to `kind === 'mechanical'` and `micro` is
   unaffected. Recorded, not blocking.
3. **`PHASE.md status` is a conformed mirror, not a second source.** Requirement
   91 mandates the field; default taken: the verifier errors on a stale mirror,
   and the `claim` verb keeps it current. The alternative (drop the
   field) contradicts the requirement and is not taken. Recorded, not blocking.

## Findings

### F0 — What "keep" means, and the one invariant

**Keep** means the verb's name, flags, output shape, and exit codes do not
change. Extending a kept verb means adding inputs or wiring it to the new derived
state without changing its existing contract. B005 never re-specifies a kept
verb; the files below are the contract.

**The invariant (B004 F0, confirmed):** every verifier-checked field has a
designated writer. Status mirrors are derived and written atomically by `claim`
under the orchestrator binding; a field with no writer is a defect against
C001–C005, not an invitation to hand-edit.

| Checked field / file | Generator | Task |
| --- | --- | --- |
| `SPEC.md` name/author/created/workspace-type | `init` / `create` | C005/C001 |
| `SPEC.md` `spec-version` | `init`, `migrate` | C005/C001 |
| `SPEC.md` `status` | `init` writes initial; `claim` (orchestrator binding) writes every transition | C005 |
| `SPEC.md` `## Tasks` rows | `new-task`, `init`, `create` add/drop; `claim` (orchestrator binding) writes a row's status | C005/C001 |
| `PHASE.md` id/objective/status/gate | `new-phase`, `init`, `migrate` create; `claim` (orchestrator binding) writes the status mirror | C005/C001 |
| `PHASE.md` review/reason/evidence | `waiver`, `new-phase`, `init` | C005 |
| `TASK.md` id/name/type/size/status/deps | `new-task`, `init`, `create` write `pending`; `claim` (orchestrator binding) writes transitions | C005/C001 |
| `GATES.md` | authored prose; templates generated by `init`/`new-task` | C002/C005 |

### F1 — Verb table

#### New verbs

All are `mf-specs <verb>`; every one accepts `--dir <workspace-root>` (default:
nearest repo root, as `author`/`which` already resolve it) and `--verbose` where
the existing commands do. "Writes" lists every file the verb may touch.

##### `init` — tier → a whole valid v2 tree

```
mf-specs init --name <slug> --tier <micro|standard|full>
  [--author <name>] [--description <text>]
  [--workspace-type in-place|worktree]
  [--phase <objective>]...                       # ordered A, B, C; default: the tier default plan
  [--task <PHASE>:<name>:<type>[:<size>][:after=<name,name>]]...
  [--review <PHASE>:required|waived]...
  [--review-reason <PHASE>:<one line>]...
  [--reviewer-profiles <slug,slug>]              # every generated review task
```

- **Writes:** `SPEC.md` (`spec-version: 2`, `status: in-progress`, name, author,
  created, placeholder Description/Requirements, a `## Creation` section
  `tier: <tier>` + `questions 0/<budget>` + `unresolved: none`, and the full
  `## Tasks` table); per phase `PHASE.md` + `MEMORY.md`; `BOARD.md` for
  `standard`/`full`; for `full`, a phase `GATES.md` with one `(mechanical)` stage
  and `PHASE.md gate: mechanical`; per work task `TASK.md` + `MEMORY.md` +
  `GATES.md` (mechanical template for execution/defect/interruptor, subjective
  template with `judge: generic-reviewer` for planning/exploratory); per
  non-waived phase a `review-phase` task (`type: review`, `reviewer-profiles`)
  after the work tasks; `MAILBOX.md` in every task for `full`, and in each task
  of a `standard` phase holding more than one task. No `sizing.json` — sizing is
  never tier-driven (B003 F3). For a waived phase it writes `review-evidence`
  naming every stage it generated (`A001:0`, `phase:0`, …) and writes **no**
  review task. The `questions n/<budget>` in `## Creation` is the creation
  run's self-reported count: no harness counter exists, so it is advisory, the
  creation orchestrator updates it before stopping, and the phase review may
  flag a mismatch when a transcript exists but cannot mechanically verify it.
- **Defaults:** `micro` and `standard` default to one
  `A:implement:execution:medium` task when none is given; `full` defaults to a
  required exploration phase A (`A:explore:exploratory:medium`) plus
  `B:implement:execution:medium`, with phase B `depends-on` the phase A task, so
  the default `full` tree has the exploration phase B003 requires. Review
  defaults are the tier contract (`micro` waived, `standard`/`full` required); a
  default `micro` waiver reason is
  `micro tier default: every task gate is the review evidence.`; task size
  `medium`. The default `micro` tree — one execution task with the review
  waived — derives a lock once that task closes and every gate is proven; no
  review task is needed and the waiver is exempt from the `records-only`
  predicate.
- **Tier validation (authoring-time, in `init` itself):** `init` reads
  `Tier.TIER_CONTRACT` and refuses a plan that violates it, before writing
  anything:
  - `init.exploration-missing` — `full` has no dedicated exploration phase A
    (the default supplies one), or a later phase does not depend on it;
    `init.exploration-forbidden` — `micro` declares an exploratory phase or
    task; `standard` declares an exploration **phase**.
  - `init.exploration-count` / `init.exploration-placement` — `standard`
    declares more than one exploratory task, or places one outside the first
    phase; `standard` may hold at most one exploratory task and only in the
    first phase.
  - `init.gate-kind` — `micro` declares a `planning` or `exploratory` task, or a
    task whose generated gate carries no command: at `micro` every file-changing
    task has a command gate, and a prose-only task means the request was not
    `micro`.
  - `init.waiver-policy` — `standard` waives a phase that holds any
    `execution`/`defect`/`interruptor` task (the `records-only` predicate in
    B003 F3); `full` waives at all (`tier.waiver-forbidden`). `micro` is exempt
    from the predicate: the appraiser may waive any `micro` phase by default and
    may upgrade an auth/data phase to `required`.
  - `init.review-task` — a waived phase would also receive a review task, or a
    required phase would not; `review-task` is generated exactly for non-waived
    phases, so `review: waived` + a review task is never produced.
    `task.review-waived` — `init` would create a `review`-type task on a phase
    whose `PHASE.md` says `review: waived` (the same rule as B004's
    `phase.waiver-with-review-task`).
- **Fails:** existing spec (`init.exists`); missing/unknown tier
  (`tier.unknown`, expected `micro, standard, full` — never a default); phase
  count outside `minPhases..maxPhases` (`init.phase-count`); work-task total or
  per-phase ceiling exceeded (`init.task-ceiling`; generated review tasks do not
  count); task naming an undeclared
  phase (`init.phase-unknown`); duplicate task name in a phase
  (`init.task-duplicate`); `after=` naming an unknown, later-phase, or
  same-named-in-two-phases task (`init.depends-unknown` / `init.depends-ambiguous`);
  `--task type: review` (`init.review-type` — init
  owns review tasks); waived override without a reason (`init.review-reason`);
  every tier-contract failure above (`init.exploration-missing`,
  `init.exploration-forbidden`, `init.exploration-count`,
  `init.exploration-placement`, `init.gate-kind`, `init.waiver-policy`,
  `init.review-task`, `task.review-waived`); invalid name/author/workspace type.
- **Tier contract is code:** it reads `Tier.TIER_CONTRACT`, never the installed
  tier file. `init` writes exactly the phase plan it is given; `new-phase`
  extends a spec past that plan.

##### `new-phase` — allocate the next phase id and its files

```
mf-specs new-phase --name <spec> --objective <one line>
  [--review required|waived] [--review-reason <one line>]
  [--gate none|mechanical|subjective] [--gate-judge <profile-slug>]
  [--board|--no-board] [--dir <root>]
```

- **Writes:** `<ID>/PHASE.md` (`id` = the allocated letter, `objective`,
  `status: pending`, `review` default `required`, `review-reason` iff waived,
  `review-evidence: phase:0` iff it writes a phase gate and the phase is waived,
  `gate` default `none`); `<ID>/MEMORY.md`; `<ID>/GATES.md` when `gate` is not
  `none` (one stage of that kind; mechanical command is
  `TODO: replace with the phase's verification command`); `<ID>/BOARD.md` unless
  `--no-board`. It creates **no tasks**; a required phase gets its review task
  from `new-task --type review` (a missing one is B004's warning
  `phase.review-task-missing`, never an error).
- **Id:** `phaseRank(max existing) + 1`, rendered to letters; never reuses a
  deleted id; `A`–`ZZ` then `phase.id-exhausted`.
- **Fails:** spec missing; `spec-version` 1 (`spec.version-outdated`, fix
  `mf-specs migrate --name <spec>`); id exhausted; waived without a reason;
  reason with `required`; gate not in the enum; subjective gate without a valid
  judge slug (`--gate-judge` defaults to `generic-reviewer`); evidence ref
  invalid; the target directory exists.

##### `new-task` — allocate the next task number in a phase

```
mf-specs new-task --name <spec> --phase <id> --task <kebab-name> --type <type>
  [--size tiny|small|medium|large] [--gates]
  [--depends-on <id,id>] [--related-tasks <id,id>]
  [--originator user|defect:<id>|planner:<id>] [--finding-ref <series>/<round>/F<n>]
  [--reviewer-profiles <slug,slug>]
  [--description <text>] [--requirement <text>]... [--dir <root>]
```

- **Writes:** `<PHASE>/<ID>-<name>/TASK.md` (`id` = `max(NNN)+1` or `001`,
  `status: pending`, `size` default `medium`, `depends-on`, `related-tasks`,
  `reviewer-profiles` only for `review`), `MEMORY.md`, `GATES.md` when
  `--gates`; appends the `SPEC.md` `## Tasks` row (sorted by `sortKey`); for a
  waived phase, appends `<ID>:0` to `review-evidence` when it writes a gate
  stage. It never writes a status transition: the task is `pending` by
  construction and `claim` under the orchestrator binding writes every later
  transition and the `PHASE.md` mirror.
- **Fails:** spec missing/v1; `spec.phase-not-found`; phase locked
  (`task.phase-locked`); 999 already used (`task.id-exhausted`); non-slug name;
  duplicate name in the phase (`task.duplicate-name`); unknown type; unknown
  size; `size: none` (`task.size-none` — complete-only); unknown/self/
  forward-phase/duplicate dependency (`task.depends-*`); `--type review` when the
  phase already holds one (`task.review-exists`); `--type review` on a phase
  whose `PHASE.md` says `review: waived` (`task.review-waived`, the same rule as
  B004's `phase.waiver-with-review-task`); `reviewer-profiles` on a
  non-review task; `--gates` on a review task; adding an
  `execution`/`defect`/`interruptor` task to a phase whose effective waiver is
  `records-only` (`task.waiver-policy`; only `standard` applies the predicate,
  `micro` is exempt); a `standard` plan gaining a second exploratory task or an
  exploratory task outside the first phase (`task.exploration-count` /
  `task.exploration-placement`).
- **Never writes a status transition.** A new task is `pending` by construction;
  `claim` is the only status generator.

##### `stamp` — the only clock

```
mf-specs stamp [--format instant|date]
```

- **Writes:** nothing. Prints `YYYY-MM-DDTHH:MM:SSZ` (default) or
  `YYYY-MM-DD` (`--format date`) from the system clock in UTC.
- **Fails:** never on valid input; an unavailable clock is exit 2. There is no
  `--at`; a caller may not invent an instant.

##### `claim` — the atomic status generator and session binding

```
mf-specs claim --name <spec> --task <id> [--session <session-id>]
  [--orchestrator]
  [--start | --close | --block --reason <one line> | --release [--force]]
```

- **Two jobs, one authority.** The default bind and `--orchestrator` form write
  the runtime binding only. `--start`/`--block`/`--close` (and an orchestrator
  `--release` that resets a task) are the **only** generator of
  verifier-checked status transitions: each writes the task `status:` in
  `TASK.md`, the matching `SPEC.md` `## Tasks` row, the `PHASE.md` status
  mirror, and the registry change in one transaction. No caller hand-edits
  those records.
- **Forms:** default is **bind** — record `{spec, task, session, at}` for the
  calling session. The transition graph is complete: `--start` moves
  `pending → in-progress`; `--block --reason` moves `pending | in-progress →
  blocked`, records the reason, and removes any binding; `--release` removes the
  binding and, when an orchestrator calls it on an `in-progress | blocked` task,
  also resets the task to `pending` (the only return path from `blocked`);
  `--close` validates that the task may close and moves `in-progress → complete`,
  then removes the binding. A blocked task resumes with `--release` then
  `--start`; no transition needs a hand edit. `--force` clears a binding owned
  by another or vanished session. Exactly one form. A second bind of a taken
  task fails.
- **Writes:** bind/release write the registry entry only (`bind` upsert;
  `close`/`block`/`release` delete). A transitioning form writes the three
  status records and the registry entry. Every file is first written to a
  sibling temp file; when all temps are staged they are renamed in
  `TASK.md` → `SPEC.md` → `PHASE.md` → registry order. If any rename fails, the
  already-renamed files are restored from their saved originals and the new
  registry entry is removed (explicit rollback), so the tree and the registry
  return to their pre-call state; no partial status write survives. Registry
  writes are temp-file-then-rename under `claims.lock` (exclusive create, 5 s
  retry).
- **`--orchestrator`:** binds `{spec, task: 'orchestrator', session}` and is how
  the execution orchestrator proves its identity to the restricted verbs.
  A spec has one orchestrator binding; a second one replaces only a vanished
  session (`--force`), otherwise `claim.orchestrator-taken`.
- **Session:** `--session`, else `OPENCODE_SESSION_ID`, else
  `claim.session-missing`. `--force` is valid only with `--release` and requires
  an orchestrator binding.
- **Who may call:** a worker may call the default **bind** for its own task and
  `--release` for its own binding; neither changes a status. Only a session
  holding the spec's **orchestrator binding** may call `--start`, `--block`,
  `--close`, an orchestrator `--release` that resets a task, `--release
  --force`, or `--orchestrator`. A worker caller is `claim.not-orchestrator`.
- **`--close` checks:** task is `in-progress` in `TASK.md`; its dependencies are
  complete; its `## Completion` checklist is fully checked
  (`claim.completion-unchecked`); and every required mechanical stage has a
  passing `GATE-RESULTS.jsonl` record (`claim.gate-unproven`). On success it
  writes all three status records atomically and removes the binding; on any
  failed check nothing is written.
- **Atomicity:** every precondition is checked before any write; a failed check
  leaves the three records and the binding untouched; a rename failure rolls all
  four files back.
- **Fails:** task already bound (`claim.taken`); bind with an incomplete
  dependency (`claim.not-ready`, naming the blockers); start a non-`pending`
  task, block a task that is neither `pending` nor `in-progress`, or close a
  non-`in-progress` task (`claim.invalid-transition`);
  close with an unchecked `## Completion` item
  (`claim.completion-unchecked`) or an unproven mechanical stage
  (`claim.gate-unproven`); missing `SPEC.md` row (`claim.row-missing`); spec
  already complete (`claim.spec-complete`); lock timeout (`claim.locked`);
  block without a reason; restricted form without an orchestrator binding
  (`claim.not-orchestrator`).
- **Scope:** `claim` is the only status generator, the only writer of a
  **session binding**, and the only verb that validates a transition before it
  writes. The graph is `pending → in-progress` (`--start`), `pending |
  in-progress → blocked` (`--block`), `blocked | in-progress → pending`
  (orchestrator `--release`), and `in-progress → complete` (`--close`); every
  status is reachable from `pending` and no transition requires a hand edit.
  `init`/`create`/`new-task` write `pending` at creation; `migrate`
  writes derived statuses; `lock` writes none.

##### `lock` — confirmation, never a stored lock

```
mf-specs lock --name <spec> --phase <id> [--dir <root>]
```

- **Writes:** nothing (not even a stale `PHASE.md status`). It is a read/derive
  confirmation verb; `claim` under the orchestrator binding keeps the status
  mirrors current and `check` reports `phase.status-stale`.
- **Exit:** 0 and `locked <phase>` iff
  `phaseComplete AND gatesProven AND (closedRound OR effectiveWaiver)` (B004
  F3); otherwise exit 1 and one line per blocking code (`task.pending`,
  `gate.unproven`, `phase.review-missing`, `phase.waiver-unproven`, …).
- **Fails:** spec/phase missing, v1 spec, a malformed phase record. There is no
  `--force`, no `--all`, and no stored list.

##### `gate run` — execute mechanical stages and record them

```
mf-specs gate run --name <spec> --phase <id>
  [--task <id>] [--stage <n> | --all] [--timeout <seconds>] [--dir <root>]
```

- **Owner:** `--task` selects the task `GATES.md` (and requires the task to be in
  `--phase`); without `--task`, the phase `GATES.md`. `--stage <n>` runs exactly
  one stage; `--all` runs every mechanical stage in ascending order and
  **continues after a failure**, recording every stage. With neither flag the
  default is every mechanical stage in ascending order and it **stops at the
  first failing stage** (already-run results stay recorded). `--stage` with
  `--all` is `gate.argument-conflict`.
- **Authority:** only a session holding the spec's orchestrator binding (B004
  F9) may run a gate; a worker caller is `gate.not-orchestrator`. This is the
  same rule as `claim --close` and `mail`.
- **Writes:** one JSON line per executed stage, appended to the owner's
  `GATE-RESULTS.jsonl` (task or phase path, B004 F5), with exactly B004's keys:
  `stage,title,kind,command,exit,verdict,at,output`. `at` comes from `stamp`.
  `output` is combined stdout+stderr, verbatim, with no truncation. It writes
  **only** `GATE-RESULTS.jsonl`; it never edits `GATES.md` or a status file.
- **Execution:** cwd = workspace root (parent of the specs store); `sh -c
  <command>`; default timeout 600 s; timeout is recorded as exit 124 and
  `verdict: fail`.
- **Exit:** 0 iff every executed stage passed; 1 if any failed or the run was
  refused; 2 internal. A failure is recorded, not thrown away.
- **Fails:** owner/gate file missing (`gate.file-missing`); unknown stage
  (`gate.stage-unknown`); unclassified stage (`gate.kind-missing`); subjective
  stage (`gate.not-mechanical`); command containing `<…>` or starting `TODO`
  (`gate.placeholder-command`); malformed existing results file
  (`gate.results-malformed`, refuse to append to a corrupt file); task/phase
  mismatch (`gate.result-owner-mismatch`); `--stage` with `--all`
  (`gate.argument-conflict`); no orchestrator binding (`gate.not-orchestrator`).

##### `gate record` — the subjective verdict

```
mf-specs gate record --name <spec> --phase <id> [--task <id>]
  --stage <n> --judge <profile-slug> --verdict pass|fail --note <text> [--dir <root>]
```

- **Writes:** one subjective JSON line (B004 F5 keys:
  `stage,title,kind,judge,verdict,at,note`) to the owner's
  `GATE-RESULTS.jsonl`. Never edits `GATES.md`, never records a mechanical stage.
- **Exit:** 0 when the record is written, whatever the verdict; 1 on refusal.
- **Fails:** mechanical stage (`gate.not-subjective`); unknown stage; bad judge
  slug; empty note; malformed existing results file.

##### `mail` — the only channel writer (B004 F8)

```
mf-specs mail --to <task-id|all> --text <text> [--phase <id>] [--session <session-id>]
  [--dir <root>]
```

- **Authority:** only a session holding the spec's **orchestrator binding** may
  call `mail` (B004 F9); a worker caller is `mail.not-orchestrator`. The sender
  is **derived from that binding**, never supplied: there is no `--from`, so a
  worker cannot send as another task or as the orchestrator. Every entry's
  sender is `orchestrator`.
- **Writes:** appends one entry to `<PHASE>/BOARD.md` (`--to all`) or
  `<TASK>/MAILBOX.md` (`--to <task-id>`), then, for a task target with a live
  claim, steers the bound session; a failed steer leaves the entry and exits 0
  with `mail.steer-failed` (warning) / `queued`. It writes **only** those channel
  files; never a status, a gate, or a registry entry.
- **Fails:** unknown recipient, board target not `all`, mailbox target ≠ owner,
  self-addressed, malformed existing file (refuse, never repair by appending),
  a board with no resolvable phase, no orchestrator binding
  (`mail.not-orchestrator`).

##### `waiver` — the generator for `PHASE.md` review decision/evidence

```
mf-specs waiver --name <spec> --phase <id> (--waived --reason <line> | --required)
  [--dir <root>]
```

- **Writes:** `PHASE.md` `review`, `review-reason`, `review-evidence`.
  `--waived` recomputes `review-evidence` from **every** classified stage in the
  phase `GATES.md` and every task `GATES.md` (phase order, then `sortKey`, then
  stage number); `--required` clears reason and evidence.
- **Fails:** spec/phase missing, v1 spec, phase locked; `--waived` with a
  `review`-type task (`phase.waiver-with-review-task`); with no stages
  (`waiver.no-stages` — B004 F12: a phase with no gates cannot waive); with an
  unclassified stage (`waiver.unclassified-stage`); with an invalid reason;
  `waiver.waiver-policy` — `full` phases never waive, and a `standard` phase
  holding any `execution`/`defect`/`interruptor` task is not `records-only`;
  `micro` is exempt from the `records-only` predicate (any `micro` phase may
  waive by default, and an auth/data phase may be upgraded to `required`).
- **Role rule (prose, C006):** only the creation orchestrator calls `waiver`;
  the execution orchestrator never converts a decision.

##### `tier` — the one tier read path (B003 F6)

```
mf-specs tier <micro|standard|full> [--dir <root>]
```

- **Writes:** nothing. Prints the installed
  `.agents/@montflow/tiers/<tier>.md` body verbatim and nothing else.
- **Fails:** unknown value (`tier.unknown`, expected `micro, standard, full`);
  missing file (`tier.missing`, fix `mf-specs doctor`); bytes differ from the
  package/embedded copy (`tier.stale`, same fix). No default, no `--all`, no

### F3 — Per-package payload manifest

#### New shared package

`packages/payload/` (`@montflow/payload`, private, no CLI, no payload of its
own), with `src/modules/manifest/`, `src/modules/install/`, and
`src/modules/embed/`. Every package with a doctor depends on it. This is the one
place compare/install/embed logic lives; the six per-package doctors become thin

`@montflow/skills` is not the home (specs/prompts/reviews/model-fallback would

#### Manifest file

One `payload.json` at each package root, next to `package.json`:

```json
{
  "schema": 1,
  "package": "@montflow/specs",
  "payloads": [
    { "kind": "skill",   "name": "montflow-create-specs", "source": "skills/montflow-create-specs", "target": ".agents/skills/montflow-create-specs" },
    { "kind": "skill",   "name": "montflow-find-specs",   "source": "skills/montflow-find-specs",   "target": ".agents/skills/montflow-find-specs" },
    { "kind": "prompt",  "name": "spec-create",           "source": "prompts/spec-create.json",      "target": ".agents/@montflow/prompts/spec-create.json" },
    { "kind": "prompt",  "name": "spec-execute",          "source": "prompts/spec-execute.json",     "target": ".agents/@montflow/prompts/spec-execute.json" },
    { "kind": "prompt",  "name": "spec-sizing",           "source": "prompts/spec-sizing.json",      "target": ".agents/@montflow/prompts/spec-sizing.json" },
    { "kind": "tier",    "name": "micro",                 "source": "tiers/micro.md",                "target": ".agents/@montflow/tiers/micro.md" }
  ]
}
```

```ts
export const PAYLOAD_KINDS = ['skill', 'profile', 'prompt', 'tier'] as const;
export type PayloadKind = (typeof PAYLOAD_KINDS)[number];

export interface PayloadEntry {
  readonly kind: PayloadKind;
  readonly name: string;      // directory name (tree) or file stem (file)
  readonly source: string;    // package-relative path
  readonly target: string;    // workspace-relative install path
}

export interface PayloadManifest {
  readonly schema: 1;
  readonly package: string;
  readonly payloads: ReadonlyArray<PayloadEntry>;
}
```

Rules:

- **Shape by kind:** `skill`/`profile` are trees (a directory of files);
  `prompt`/`tier` are single files. `source`/`target` are explicit, so there is
  no second path table and no `*_NAMES` array.
- **Closed union:** adding a kind is a code change plus path tests, never a
  string in a package manifest alone.
- **No hardcoded names:** the six arrays replaced are
  `SPEC_SKILL_NAMES`/`SPEC_PROMPT_NAMES`
  (`packages/specs/src/modules/doctor/doctor.module.ts:6,19`), `SKILL_NAMES`
  (`packages/skills/src/apps/doctor/doctor.apps.module.ts:16`), `SKILL_NAMES`
  (`packages/prompts/src/apps/doctor/doctor.apps.module.ts:24`), `SKILL_NAMES`
  (`packages/reviews/src/apps/doctor/doctor.apps.module.ts:17`), `SKILL_NAMES`
  (`packages/references/src/apps/doctor/doctor.apps.module.ts:26`), and
  `PROMPT_NAMES`
  (`packages/model-fallback/src/apps/doctor/doctor.apps.module.ts:12`).
  `SPEC_SKILL_NAMES`, `SPEC_PROMPT_NAMES`, `SKILL_NAMES`, and `PROMPT_NAMES`
  are derived from the manifest (`namesOf(manifest, kind)`); only non-payload
  checks (`references`' `CHECK_NAMES`, `RETIRED_SKILL_NAMES`) stay constants.
  `modules/prompt/prompt.module.ts:29` keeps `PROMPT_NAMES = SPEC_PROMPT_NAMES`;
  `SPEC_PROMPT_NAMES` is the derived manifest list, so the re-export needs no
  edit.
  `SPEC_TIER_NAMES` stays `TIERS` as B003 F6 requires; the manifest test
  asserts the `tier` entry names equal `TIERS`, so the enum and the payload
  cannot drift.
- **One reader:** `loadManifest(packageRoot)` imports `payload.json` (a JSON
  module, so the compiled binary carries it) and validates:
  `(kind,name)` unique; `name` a slug/file stem; `source` exists and is inside
  the package; `target` under the kind's allowed root; no path escapes; every
  package with a `doctor` has a manifest; every package with a manifest has a
  `doctor`; every kind in `PAYLOAD_KINDS` has a target root.
- **One engine:** `runPayloadDoctor(root, manifest, { check })`:
  - Resolve each entry: package path first, `EMBEDDED_PAYLOAD[kind][name]`
    second. Filesystem wins so a source checkout needs no regeneration.
  - Compare trees by the files the package ships, byte for byte; extra installed
    files are user data, never drift and never deleted.
  - Atomic writes (sibling temp + rename); never write through a symlink; a
    symlinked tree is `blocked` in both modes.
  - Status vocabulary: check `ok | missing | stale | mismatched | blocked`;
    repair `present | installed | repaired | blocked`. `stale` = same file set,
    different bytes; `mismatched` = the package's file set is missing/extra
    entries (today's `mismatched`, kept); `blocked` = repair cannot clear it.
    `unhealthy` = `missing|stale|mismatched|blocked`; `repairable` =
    `missing|stale|mismatched`. `doctor --check` exits 1 on unhealthy.
  - `check` performs no writes at all: no temp file, no `makeDirectory`.
- **Report-only parity test:** `packages/payload/src/modules/install/tests/`
  covers stale/missing/mismatched, symlink, blocked, and "check writes nothing";
  a second test reads root `package.json` and fails if any `mf-*:check` script
  invokes `doctor` without `--check`, or if a package with a doctor is absent
  from `mf:check`.

#### Embedded payload

- One generator implementation:
  `packages/payload/src/modules/embed/embed.module.ts` exports
  `generateEmbeddedPayload({ packageRoot, manifest, output })`; it reads each
  entry, refuses a tree without its required file (`SKILL.md` for a skill,
  `PROFILE.md` for a profile), and writes
  `export const EMBEDDED_PAYLOAD: Record<PayloadKind, Record<string, Record<string,string>>>`
  (every payload is a file map keyed by relative path).

- Every package keeps `tests/embedded-payload.test.ts` (existing pattern),

- `packages/*/package.json` gains a `files` array naming `payload.json`, the

### F6 — Missing payload in an installed package: never silent

The contract for every doctor, every mode:

1. **Manifest absent/unreadable/empty** (`payload.json` missing, not JSON, or
   `payloads: []`): `blocked`, code `doctor.manifest-missing`, exit 1. An absent
   manifest is never read as "nothing to install", because that would report a
   broken package as healthy.
2. **Entry source absent and not embedded**:
   `blocked`, code `doctor.payload`, exit 1. The message names the artifact and
   both repair steps:

   ```
   packaged <kind> '<name>' is missing at '<source>' and is not embedded in this build.
     Fix: reinstall @montflow/<package>, then run `mf-<tool> doctor`.
   ```

3. **Entry source absent but embedded** (compiled binary or a broken checkout):
   use the embedded bytes, report `source: embedded in this build`; not an
   error. This is why the compiled binary keeps working.
4. **Installed copy missing/stale/mismatched:** `missing`/`stale`/`mismatched`,
   repairable, and the report's fix line is exactly `Run: mf-<tool> doctor`.
   `blocked` statuses never print that line, because repair cannot clear them.
5. **A blocked payload never aborts the rest of the run** (existing rule): every
   other entry is still checked/installed, and the aggregate exits 1.
6. The repair hint always names the **owning** CLI (`mf-specs`, `mf-profiles`,
   `mf-skills`, …), never a generic `mf-specs doctor` for another package.

A verifier reads the same manifest: `check`-mode and repair-mode are the same
engine with `check` toggled, so a payload cannot be installable but unverifiable
or vice versa.

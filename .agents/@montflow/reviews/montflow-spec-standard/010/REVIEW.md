### F23 — A resumed owner still appends an authoritative failure record after the newer attempt's pass, so `check` reports the stage unproven

- Severity: Major
- Location: `packages/specs/src/modules/scheduler/scheduler.module.ts:815-871`, `packages/specs/src/apps/cli/cli.gate.run.module.ts:889-910`, `packages/specs/src/modules/gates/gates.module.ts:802-807`
- Status: Open
- Attempts: 1
- First Seen: 009
- Problem: F22's guard makes `finish` skip the terminal state write when the last attempt is not the finisher's (`scheduler.module.ts:829-834`), but the next statement appends the finisher's record unconditionally (`const index = yield* persist(outcome)`, `:842`). `check` treats the last record per stage in file order as authoritative (`latestResults`, `gates.module.ts:802-807`), and a complete owner whose latest mechanical record is not a pass is `gate.unproven` (`:901-921`). Trigger: owner A is paused past its lease, B reclaims attempt 2 and passes, A resumes and fails. A's state write is correctly skipped (state stays `passed`, `attempts[1].owner.session === 's2'`, `exit 0`, `resultIndex 0`), but A's `fail`/`exit 7` record is appended after B's pass. Reproduced with the shipped `scheduleRun` plus `verifyGateResults` on a temp workspace: the results file is `[{owner: s2, verdict: pass}, {owner: s1, verdict: fail}]` and verification of a complete owner returns `gate.unproven: … has no recorded passing result (latest verdict fail)`, while the scheduler's state is `passed`. The F22 regression test asserts only the state and the third requester, never the results file, so it stays green.
- Impact: a key that genuinely passed is reported failed by `check` and `check --require-complete`, so the owning task or phase cannot close until the gate is rerun; the scheduler's "reuse the pass" decision and the record ledger disagree on the same key. C5/C6 assume the run state and the record ledger tell one story, so this is F22's class one layer down.
- Suggestion: do not append an authoritative record for an attempt that is no longer last. Either skip `persist` when the terminal-write guard skips (return the local outcome for the caller's report only), or append a `reused: true` record sourced from the state's current `resultIndex` so the effective record remains the newer attempt's pass. Add a regression test that asserts the effective record after A resumes is B's pass, not A's failure.

#### Discussion

<!-- Append-only. Each turn prefixed by its role tag. -->

- [Reviewer] Found by re-reading F22's fix: the guard returns from the state write but the `persist` call after it is unguarded. Reproduced with the shipped scheduler and verifier (`gate.unproven` while the run state is `passed`).

- [Fixer] The record append is now conditional on the same ownership guard as the terminal write. `packages/specs/src/modules/scheduler/scheduler.module.ts:815-843` returns `owned` from the locked terminal write: `:828-840` returns `false` when `state.attempts.length !== attempt` or the last attempt's `owner.session` is not this request's, and only the owned path writes the state. `:849-871` runs `persist` and the pointer write only when `owned`; an attempt that is no longer last returns its local outcome for the caller's report and appends no record, so `latestResults` keeps the newer attempt's pass. `pruneRunStates` still runs on every path (`:872`). Trigger addressed: A pauses past its lease, B reclaims attempt 2 and passes, A resumes and fails — the state stays `passed` and `GATE-RESULTS.jsonl` keeps B's single pass instead of appending A's `fail` after it, so `gate.unproven` can no longer fire against a scheduler state of `passed`. Extended the existing F22 regression `a resumed owner cannot clobber the attempt that reclaimed its lease` (`packages/specs/src/modules/scheduler/tests/scheduler.test.ts:578-694`): its persist callbacks now write mechanical stage-0 records (`persistStage`, `:45-70`), and after A resumes the test asserts the results file has exactly one record, `latestResults(records).get(0)` is a `pass` owned by `s2`, and `verifyGateResults({ gates: <stage 0 mechanical, command 'printf ok', scope repo>, results, complete: true, owner: 'A001' })` returns `valid: true` with no issues (`:657-679`). With `persist` made unconditional again the same test fails at `expected [ { stage: +0, …(11) }, …(1) ] to have a length of 1 but got 2`; it passes with the guard. Verified: `bun run --cwd packages/specs test -- src/modules/scheduler/tests/scheduler.test.ts` (2 files, 36 tests passed), `bun run --cwd packages/specs ts:check` (clean); `lint:check` and `format:check` report only pre-existing untracked files (`packages/specs/test_c005*.ts`, `src/modules/board/board.module.ts`) and nothing under the changed files. No deviation: the first option in the Suggestion (skip `persist`, return the local outcome for the report) was taken; the `reused: true` alternative was not needed.

- [Reviewer] The reclaim-before-finish path this finding reproduced is fixed: `owned` is read under `RUNS_LOCK_FILE` (`scheduler.module.ts:815-847`), attempts only append, and the guard returns `false` for a finisher whose attempt is no longer last, so the state and the record are both skipped; the extended regression at `scheduler.test.ts:578-694` drives A paused past its lease, B reclaiming attempt 2 with a pass, then A resuming and failing, and it now asserts exactly one record (B's pass) plus a clean `verifyGateResults`. The same claim does not hold for the general case, though, because `persist` runs after the lock is released (`:849-850`): ownership is checked once, before the terminal write, and nothing stops a new attempt from claiming the key between that check and the append's completion. `finish` writes `state: failed` for a failed attempt, which is terminal-but-not-passed, so a second requester's `step()` skips reuse/running/reclaim and claims attempt n+1 immediately — no lease reclaim is needed. Reproduced with the shipped `scheduleRun`: A runs attempt 1, fails, and its persist callback sleeps 300ms (a paused process or a slow append); 20ms later B claims attempt 2, passes, and appends at once; A's append then lands. The ledger is `[ {owner: s2, verdict: pass}, {owner: s1, verdict: fail} ]`, the state is `passed` with `resultIndex: 0`, and `verifyGateResults` with `complete: true` returns `valid: false` with `gate.unproven` — F23's exact impact, with the ownership loss happening during the append instead of before it. The regression test misses it because B reclaims while A is still executing (so the guard sees `attempts.length !== attempt`), never after A has passed the guard. The comment at `:828-832` ("a resumed owner writes neither state nor record") therefore overstates the guarantee; the finding's stated invariant, that an attempt no longer last never appends an authoritative record, is not enforced. Keeping Open: make the append part of the same `RUNS_LOCK_FILE` critical section as the terminal write (it is one line, not the command), or have `latestResults`/`check` prefer the record at the terminal state's `resultIndex` (or the highest attempt) instead of file order, and add a regression where A's append is delayed until after B's pass.

### F24 — The pre-pass fingerprints every selected stage before any stage runs, so an earlier stage's writes make a later stage's recorded key stale

- Severity: Major
- Location: `packages/specs/src/apps/cli/cli.gate.run.module.ts:739-767`, `packages/specs/src/apps/cli/cli.gate.run.module.ts:828`, `packages/specs/src/apps/cli/cli.gate.run.module.ts:870`
- Status: Resolved
- Attempts: 1
- First Seen: 009
- Problem: F20's existence check calls `fingerprintOf(scopes, stageLabel(index))` for every selected stage inside the pre-pass (`:829`). `fingerprintOf` caches by `scopes.join(',')` (`:740-767`), and the loop's later `fingerprintOf(scopes)` (`:871`) returns that cached print, so each stage's key is computed from the tree as it stood *before* the first stage ran. Trigger, reproduced with the shipped CLI on a temp workspace: a two-stage task gate where stage 0 is `touch built.txt` with `scope: app` and stage 1 is `true` with `scope: repo`; `gate run --task A001 --all` prints `2/2 stages passed`, and the very next `check` reports `gate.stale-result` for stage 1 — its key embeds the pre-run fingerprint, while `check` recomputes after `built.txt` exists (`… records a pass for stage 1 under key …, but the current inputs recompute to …`). Stage 0 stays fresh because nothing in its own scope changed. Before this pre-pass, stage 1's print was computed in the loop after stage 0 ran, so the same run verified clean.
- Impact: a multi-stage run that just passed leaves `check` red, so the task cannot close until every later stage is rerun standalone; the recorded key for the later stage does not describe the inputs it actually verified. The effect is silent in the run output and surfaces only on the next `check`.
- Suggestion: keep F20's existence check but do not seed the key cache from it — call `fingerprintScopes` directly in the pre-pass (it only needs `missing`), or key the cache by stage so each loop iteration fingerprints the current tree — and add a test where stage 0 writes a file inside stage 1's scope and `check` stays clean after `--all`.

#### Discussion

<!-- Append-only. Each turn prefixed by its role tag. -->

- [Reviewer] Found by re-reading F20's pre-pass against `fingerprintOf`'s cache. Reproduced end to end with the shipped CLI: a clean `--all` run followed by `check` yields `gate.stale-result` for the later stage.

- [Fixer] The pre-pass no longer seeds a key cache. `packages/specs/src/apps/cli/cli.gate.run.module.ts:739-765` removes the `prints` map: `fingerprintOf` calls `fingerprintScopes` on every call and caches nothing. The existence check in the pre-pass (`:828`) and the loop's print (`:870`) therefore each fingerprint the tree as it stands — the pre-pass before the first stage, the loop after the earlier stages wrote — so each recorded key describes the inputs that stage actually verified. Trigger addressed: stage 0 `touch built.txt` with `scope: app`, stage 1 `printf two` with `scope: repo`; `gate run --task A001 --all` now records stage 1 under the post-`touch` fingerprint, so the next `check` recomputes the same key and stays clean. Regression test `keeps check clean after --all when an earlier stage writes in a later scope` (`packages/specs/src/apps/cli/tests/gate-scheduler.test.ts:508-536`) asserts both stages pass, `built.txt` exists at the workspace root, and `check` reports no `gate.stale-result`; with the pre-pass cache restored the same test fails at `expected [ 'gate.shared-check-in-task', …(4) ] to not include 'gate.stale-result'`. Deviation: the reviewer's first option (call `fingerprintScopes` directly, keep no cache) was taken rather than keying the cache per stage; a cross-stage cache is stale by construction because stages run in order and may write inside a later stage's scope. Verified: `bun run --cwd packages/specs test -- src/apps/cli/tests/gate-scheduler.test.ts` (2 files, 28 tests passed), `bun run --cwd packages/specs ts:check` (clean); `lint:check`/`format:check` report only the pre-existing untracked files named in the F23 turn.

- [Reviewer] Confirmed in the code and by the scoped suite. `fingerprintOf` (`cli.gate.run.module.ts:739-765`) is now a thin `fingerprintScopes` call with no map, so the pre-pass check at `:828` and the per-stage key at `:870` are independent reads of the tree at their own turn; `fingerprintScopes` itself (`scheduler/fingerprint.module.ts:47-105`) caches nothing. The pre-pass still resolves each selected stage's scope (`:775`), validates it, and fingerprints it for existence only, which is what F20 needs. `--stage` validates and fingerprints only the named stage (`selection.stages`), the default selection all mechanical stages, and a phase gate's fallback resolves `['repo']` (`ownerScope`, `:539-546`) before the loop, so no path reuses a pre-run print. The regression at `gate-scheduler.test.ts:508-536` (stage 0 `touch built.txt` in `app`, stage 1 `printf two` in `repo`, then `check` clean) passes. Removing the cache makes the pre-pass walk each scope once more per stage; that is the cost of correctness, not a defect. Resolved.

### F25 — `create --tasks` absorbs a later bare-name task into the preceding `scope=` list

- Severity: Minor
- Location: `packages/specs/src/apps/cli/cli.shared.module.ts:717-754`, `packages/specs/README.md:86-96`, `packages/specs/src/apps/cli/cli.create.module.ts:491-497`
- Status: Resolved
- Attempts: 1
- First Seen: 009
- Problem: `scaffoldTaskSpecs` keeps a comma fragment inside the current task whenever the task is in a `scope=` field and the fragment contains no `:` (`:724-726`). A task entry's grammar allows a bare name (`name[:type[:gates[:size]]]`), so `--tasks "first:execution:scope=app,build"` is parsed as one task with `write-scope: app,build` instead of two tasks (`first`, `build`). Reproduced on the shipped CLI in a temp dir: one `A/A001-first/TASK.md` with `write-scope: app,build`, no `A002-build`; before F21's fix the old `csv` split produced both tasks. The merge is silent because `app,build` is valid scope grammar, so `create` and `check` both stay green.
- Impact: a task the author asked for disappears, its name becomes a scope path, and the scaffolded tree looks valid — the same silent-misparse class F21 filed. It bites whenever a later entry is a bare name, a common short form (`…,build`, `…,docs`).
- Suggestion: split task entries on a delimiter that cannot appear in a scope (`;` or a repeated `--task`), or require `scope=` to be the final field and refuse a following colon-less fragment with a diagnostic that names the ambiguity; add a test for `first:execution:scope=app,build`.

#### Discussion

<!-- Append-only. Each turn prefixed by its role tag. -->

- [Reviewer] Found while re-testing F21's fix with a second bare-name task. Confirmed with the shipped CLI (one task, `write-scope: app,build`); the README now documents the colon rule, but the task grammar still allows a bare name, so the command has no unambiguous reading.

- [Fixer] `--tasks` now has a deterministic, loud separator. `packages/specs/src/apps/cli/cli.shared.module.ts:700-768` gives `scaffoldTaskSpecs` a result type and a `;` task separator: it splits on `;` first (`:722-725`), keeps a comma inside `scope=` in that scope (`first:execution:scope=app,lib` → one task, `write-scope: app,lib`), and keeps a comma as a task separator when the current entry has no `scope=` field (`first:execution,second:execution` → two tasks). A colon-less fragment after a `scope=` field that is followed by another fragment is refused with `cli.invalid-argument`, naming both readings and the unambiguous `;` form (`:743-750`); both `--tasks` surfaces carry the refusal — the CLI handler at `packages/specs/src/apps/cli/cli.create.module.ts:511-529` and the slash parser at `packages/specs/src/apps/cli/cli.slash.parse.module.ts:351-362` (`taskError` on `SlashArgs`, `:265`, `:481`) with the refusal rendered at `packages/specs/src/apps/cli/cli.slash.module.ts:268-277`. `packages/specs/README.md:84-101` documents `;`, the no-scope comma rule, the in-scope comma, and the refusal. Tests: `Cli.scaffoldTaskSpecs grammar` (`packages/specs/src/apps/cli/tests/create.test.ts:334-363`) covers the no-scope comma, the in-scope comma, `;`, and the refusal; `:398-415` runs `create --tasks "first:execution:scope=app;build"` to two tasks, `:417-429` asserts the refusal names the ambiguity and `;` form and writes nothing, and `:431-444` asserts `init --task A:first:execution:medium:scope=app,lib` keeps one task with `write-scope: app,lib`.
  Deviation, stated plainly: the instructed third shape `first:execution:scope=app,build` is syntactically identical to the instructed first shape `first:execution:scope=app,lib` — both are a colon-less fragment after `scope=` with no `:` — so no parser can accept one as a scope list and refuse the other without a lexical guess about which words are paths. I kept the comma-in-scope form that the first bullet and F21's resolved regression test require, and refuse the ambiguity that is detectable: a colon-less scope continuation followed by another fragment (`first:execution:scope=app,build,second:execution`). If the intent is instead to refuse every `scope=…,<colon-less>` tail, that reverses F21's documented form and its test; say so and the splitter plus that test switch together. Verified: `bun run --cwd packages/specs test -- src/apps/cli/tests/create.test.ts` (2 files, 70 tests passed), `bun run --cwd packages/specs ts:check` (clean); `lint:check`/`format:check` report only the pre-existing untracked files named in the F23 turn.

- [Reviewer] Judged against the shipped grammar, not the contradiction in the brief. The splitter is deterministic (`cli.shared.module.ts:717-754`): `;` always starts a task; a comma starts a task when the current entry has no `scope=` field or the next fragment carries a `:`; a colon-less fragment after `scope=` merges when it is the segment's last fragment and is refused when another fragment follows. The same helper backs the CLI handler (`cli.create.module.ts:511-529`) and the slash parser (`cli.slash.parse.module.ts:351-362` → `cli.slash.module.ts:268-277`), so the two surfaces cannot drift. `--tasks "first:execution:scope=app,build"` is now the documented one-task rule (README `:86-96`, help `:491-497`: "inside scope= it stays in that scope", with `;` for a following bare-name task), and the only input with two live readings (`scope=app,build,second:execution`) is refused before anything is written; the temp-dir run confirms exit 1 with no spec directory. The F21 two-path form is unchanged. This resolves the silent-misparse trigger F25 named — the bare-name task is no longer swallowed without a documented rule. The refusal's cost for a three-path scope is a separate defect and is filed as F26.

### F26 — `create --tasks` refuses a three-path scope, and its diagnostic names the wrong fragment

- Severity: Minor
- Location: `packages/specs/src/apps/cli/cli.shared.module.ts:743-750`, `packages/specs/README.md:88-96`, `packages/specs/src/apps/cli/cli.create.module.ts:491-497`
- Status: Open
- Attempts: 0
- First Seen: 010
- Problem: the ambiguity refusal fires on any colon-less scope continuation that is not the segment's last fragment (`if (index < fragments.length - 1)`), so a three-path scope is rejected even though a scope list is comma-separated by design. `bun run --cwd packages/specs cli create --tasks "first:execution:scope=app,lib,docs"` exits 1 with `cli.invalid-argument`; the same scope is accepted by `init --task A:first:execution:medium:scope=app,lib,docs` (writes `write-scope: app,lib,docs`) and by `isScopeList` (`scheduler/scope.module.ts:29-35`). The diagnostic is also wrong for this input: it quotes `'first:execution:scope=app,lib'` and says `'lib' could be another scope path or a new task`, then suggests `'first:execution:scope=app;lib'` — `lib` is plainly the second scope path, and the `;` rewrite would keep only `app` in scope while turning `lib` and `docs` into tasks. The help text (`cli.create.module.ts:491-497`) and README (`:88-96`) say a comma inside `scope=` stays in that task's scope list, which is false for the third path; only the README's refusal clause mentions the cut-off.
- Impact: `create --tasks` cannot express a three-or-more-path `write-scope`, so an author leaving `init` for `create` must scaffold the task and hand-edit `TASK.md`; following the printed `fix` silently drops two declared scope paths and creates two phantom tasks, the exact failure class F21/F25 are about. The surface disagrees with `init` and with its own help. The refusal is loud, so an untouched tree is the outcome; the damage comes only from following the suggested rewrite.
- Suggestion: make the rule uniform — every colon-less fragment after a `scope=` field stays in that scope (tasks after a scope list always need `;`), which keeps F25's two-fragment behaviour and accepts `app,lib,docs`; drop the mid-list refusal, or, if the refusal is kept, refuse the whole `scope=` list whenever another fragment follows and name the fragment that could be a task, never a valid scope path. Add `scope=app,lib,docs` to `Cli.scaffoldTaskSpecs grammar` and a `create` test asserting one task with `write-scope: app,lib,docs`.

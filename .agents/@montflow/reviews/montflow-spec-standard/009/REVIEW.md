### F22 — The terminal state write still marks whichever attempt is last finished, so a resumed owner clobbers a reclaimed attempt

- Severity: Major
- Location: `packages/specs/src/modules/scheduler/scheduler.module.ts:796-829`, `packages/specs/src/modules/scheduler/scheduler.module.ts:690-703`
- Status: Resolved
- Attempts: 1
- First Seen: 008
- Problem: `finish` writes `terminalState(state)` under `runs.lock` without checking that the last attempt is its own: `terminalState` (`:796-809`) sets `state.state = phase`, rewrites `state.attempts[length - 1]` with the finisher's `finishedAt`/`exit`/`durationMs`, and filters only the finisher's own session from `waiters`. F16's guard covers the later pointer write, not this write. Trigger: an owner's lease expires while it is still alive (step 3, `:690-703`, reclaims it: a paused process — suspended container, laptop sleep, SIGSTOP — or a heartbeat whose best-effort write fails for `leaseSeconds`). A second requester then claims attempt n+1 (`:716-734`) and starts running; when the earlier owner resumes and finishes, its terminal write overwrites attempt n+1's entry and resets the key's state to the *earlier* owner's phase. Reproduced with the shipped CLI in a temp workspace: `gate.json` `leaseSeconds: 2`, `heartbeatSeconds: 1`; stage 0 command stops its own parent (`kill -STOP $PPID`, resumed by a background `sleep 4; kill -CONT`), exits 7, and skips the stop when `.stopped` exists. A stops right after claiming attempt 1; B reclaims at ~2.5s, runs, and lands `state: "passed"`, `resultIndex: 0`, `attempts[1].exit: 0`. A resumes at ~4s and the state becomes `state: "failed"` with `attempts[1].exit: 7`, `durationMs: 4010`, `resultIndex` still 0 (B's pass record). A third requester C then reruns the key (`3` executions of one key, records `pass(sess-b)`, `fail(sess-a)`, `pass(sess-c)`), and `check` exits 1 because the newest record is A's failure. `consume` on that state would report `state: failed` with `exit: 0`, the pointer's pass record.
- Impact: a key that already passed is re-opened and re-run after a pause, so a heavy command executes again with nothing changed; a stale failure from the paused owner is appended last and turns `check` red; a waiter can be handed a state/exit pair that disagrees. It is the same "a newer live attempt must keep its owner, its lease, and its `running` phase" invariant the F16 guard cites, and the reclaim path is the ordinary C8 recovery, not an exotic one.
- Suggestion: guard the terminal write the same way as the pointer — read the state, and if `state.attempts.length !== attempt` (or the last attempt's owner is not this request's owner), record the outcome without rewriting the state, so a reclaimed attempt keeps running; a finisher whose attempt is no longer last must not change the key's state or any attempt entry. Optionally have `consume` prefer the state's `resultIndex` record over the attempt fields when the two disagree.

  Deviation, stated plainly: the instructed third shape `first:execution:scope=app,build` is syntactically identical to the instructed first shape `first:execution:scope=app,lib` — both are a colon-less fragment after `scope=` with no `:` — so no parser can accept one as a scope list and refuse the other without a lexical guess about which words are paths. I kept the comma-in-scope form that the first bullet and F21's resolved regression test require, and refuse the ambiguity that is detectable: a colon-less scope continuation followed by another fragment (`first:execution:scope=app,build,second:execution`).

### F16 — The post-append `resultIndex` write can mark a newer attempt finished and re-open single flight

- Severity: Major
- Location: `packages/specs/src/modules/scheduler/scheduler.module.ts:831-839`, `packages/specs/src/modules/scheduler/scheduler.module.ts:796-809`
- Status: Resolved
- Attempts: 1
- First Seen: 007
- Problem: `finish` writes the terminal state (state `failed`/`timeout`/`cancelled`) at `:823`, appends the record at `:830`, then rebuilds a terminal state from a *fresh* read and writes it again to add `resultIndex` (`:831-839`). `terminalState` (`:796-809`) always rewrites the **last** attempt to `finishedAt: at` with the owner's `exit`/`durationMs` and resets `state` to the owner's phase. Between the first terminal write and the pointer write the key is terminal, so another requester's `step()` (step 4, `:704-740`) can legitimately claim attempt n+1. The pointer write then marks that live attempt finished and sets the state back to `failed`, dropping its `waiters`. Reproduced with the shipped `scheduleRun`: owner A fails and its append takes 300ms; B claims attempt 2 and runs 400ms; A's pointer write leaves `state: "failed"`, `attempts[1].exit: 1`, and `attempts[1].finishedAt` set while B is still running; requester C then claims attempt 3 and its execute starts (`events: ["B-start","C-start"]`) before B finishes. A waiter registered on attempt 2 also consumes the clobbered state, reads `resultIndex` 0, and reports attempt 1's record as attempt 2's outcome — the F1 class again.
- Impact: two concurrent executions of one key and two heavy commands despite `lanes: 1`, plus a waiter told a previous attempt's failure as its own result. The window is the append plus the lock and write (small, but widened by contention or a slow filesystem) and it sits on the ordinary fail-then-retry path, with no lease expiry involved.
- Suggestion: make the pointer update conditional on the attempt it belongs to — read the state and write only when `state.attempts.length === attempt` and `state.state === phase` (the guard `heartbeatLoop` already uses at `:981-988`); otherwise leave the state alone, because `consume` already falls back to the attempt's exit fields. Alternatively carry the record index from the single terminal write.

### F22 — The terminal state write still marks whichever attempt is last finished, so a resumed owner clobbers a reclaimed attempt

- Severity: Major
- Location: `packages/specs/src/modules/scheduler/scheduler.module.ts:796-829`, `packages/specs/src/modules/scheduler/scheduler.module.ts:690-703`
- Status: In Review
- Attempts: 1
- First Seen: 008
- Problem: `finish` writes `terminalState(state)` under `runs.lock` without checking that the last attempt is its own: `terminalState` (`:796-809`) sets `state.state = phase`, rewrites `state.attempts[length - 1]` with the finisher's `finishedAt`/`exit`/`durationMs`, and filters only the finisher's own session from `waiters`. F16's guard covers the later pointer write, not this write. Trigger: an owner's lease expires while it is still alive (step 3, `:690-703`, reclaims it: a paused process — suspended container, laptop sleep, SIGSTOP — or a heartbeat whose best-effort write fails for `leaseSeconds`). A second requester then claims attempt n+1 (`:716-734`) and starts running; when the earlier owner resumes and finishes, its terminal write overwrites attempt n+1's entry and resets the key's state to the *earlier* owner's phase. Reproduced with the shipped CLI in a temp workspace: `gate.json` `leaseSeconds: 2`, `heartbeatSeconds: 1`; stage 0 command stops its own parent (`kill -STOP $PPID`, resumed by a background `sleep 4; kill -CONT`), exits 7, and skips the stop when `.stopped` exists. A stops right after claiming attempt 1; B reclaims at ~2.5s, runs, and lands `state: "passed"`, `resultIndex: 0`, `attempts[1].exit: 0`. A resumes at ~4s and the state becomes `state: "failed"` with `attempts[1].exit: 7`, `durationMs: 4010`, `resultIndex` still 0 (B's pass record). A third requester C then reruns the key (`3` executions of one key, records `pass(sess-b)`, `fail(sess-a)`, `pass(sess-c)`), and `check` exits 1 because the newest record is A's failure. `consume` on that state would report `state: failed` with `exit: 0`, the pointer's pass record.
- Impact: a key that already passed is re-opened and re-run after a pause, so a heavy command executes again with nothing changed; a stale failure from the paused owner is appended last and turns `check` red; a waiter can be handed a state/exit pair that disagrees. It is the same "a newer live attempt must keep its owner, its lease, and its `running` phase" invariant the F16 guard cites, and the reclaim path is the ordinary C8 recovery, not an exotic one.
- Suggestion: guard the terminal write the same way as the pointer — read the state, and if `state.attempts.length !== attempt` (or the last attempt's owner is not this request's owner), record the outcome without rewriting the state, so a reclaimed attempt keeps running; a finisher whose attempt is no longer last must not change the key's state or any attempt entry. Optionally have `consume` prefer the state's `resultIndex` record over the attempt fields when the two disagree.

#### Discussion

<!-- Append-only. Each turn prefixed by its role tag. -->

- [Reviewer] Found by re-reading F16's fixed guard: it is applied to the post-append pointer write only, while `terminalState` (`:796-809`) — called unguarded at `:823` — has the identical "rewrite the last attempt" shape. Reproduced end to end with the CLI (two `gate run` processes, a stage that `kill -STOP`s its own parent and resumes it after the 2s lease): B's `passed` attempt 2 is overwritten with A's `failed`/`exit 7`, a third requester runs the same key again, and `check` reports `1 failed`.
- [Fixer] The terminal write is now conditional on the attempt it belongs to, the same guard the pointer write uses. `packages/specs/src/modules/scheduler/scheduler.module.ts:823-834` reads the state under `runs.lock` and returns without writing when `state.attempts.length !== attempt` or the last attempt's `owner.session` is not this request's owner; the existing `SchedulerWriteError` for a missing state is unchanged. Because attempts only ever append (`:729`), `length === attempt` can only be true while this finisher still owns the last attempt, so a lease reclaimed while its owner was paused (the step 3 path at `:690-703`) keeps the newer attempt's owner, lease, `exit`, `finishedAt`, and the key's phase. The outcome is still recorded: `persist(outcome)` at `:842` appends the finisher's own record, and the post-append pointer write at `:854-856` already skips on the same shape, so `resultIndex` keeps pointing at the newer attempt's record. ### F21 — `create --tasks` splits on commas, so a documented multi-path `scope=` silently becomes a second task

- Severity: Minor
- Location: `packages/specs/src/apps/cli/cli.create.module.ts:510`, `packages/specs/src/apps/cli/cli.create.module.ts:283-334`, `packages/specs/README.md:87-95`
- Status: In Review
- Attempts: 1
- First Seen: 008
- Problem: the help and README document the scope token as `scope=path,path`, but the handler splits the whole `--tasks` value on commas before the parser ever sees it (`const taskSpecs = csv(opt(config.tasks))`, `:510`). The parser's comma-separated scope list is therefore unrepresentable through `--tasks`. Reproduced: `mf-specs create --name c3 --tasks "first:execution:gates:medium:scope=app,lib"` creates two tasks — `A001-first` with `size: medium`, `write-scope: app` — and a phantom `A002-lib` with an empty `write-scope:`; `check` then reports `0 failed` with only warnings, so nothing signals the misparse. `init` is unaffected (its `--task` flag repeats instead of splitting), and `init --task A:first:execution:scope=app,lib` writes `write-scope: app,lib`.
- Impact: an author who follows the documented grammar gets a task named after the second scope path, half of the declared scope silently dropped, and a second execution task with no declared scope — the exact collision protection `phase.write-scope-overlap` needs to be sound. The failure is silent whenever the stray path happens to be a valid kebab-case name (`lib`, `app2`, `docs`); the tree still verifies.
- Suggestion: split `--tasks` on a delimiter that cannot appear inside a scope (`;` or a repeated `--task` flag), or teach `csv` to respect the `scope=` field boundaries; add a test that `first:execution:scope=app,lib` yields one task with `write-scope: app,lib`.

### F23 — A resumed owner still appends an authoritative failure record after the newer attempt's pass, so `check` reports the stage unproven

- Severity: Major
- Location: `packages/specs/src/modules/scheduler/scheduler.module.ts:815-871`, `packages/specs/src/apps/cli/cli.gate.run.module.ts:889-910`, `packages/specs/src/modules/gates/gates.module.ts:802-807`
- Status: Resolved
- Attempts: 2
- First Seen: 009
- Problem: F22's guard makes `finish` skip the terminal state write when the last attempt is not the finisher's (`scheduler.module.ts:829-834`), but the next statement appends the finisher's record unconditionally (`const index = yield* persist(outcome)`, `:842`). `check` treats the last record per stage in file order as authoritative (`latestResults`, `gates.module.ts:802-807`), and a complete owner whose latest mechanical record is not a pass is `gate.unproven` (`:901-921`). Trigger: owner A is paused past its lease, B reclaims attempt 2 and passes, A resumes and fails. A's state write is correctly skipped (state stays `passed`, `attempts[1].owner.session === 's2'`, `exit 0`, `resultIndex 0`), but A's `fail`/`exit 7` record is appended after B's pass. Reproduced with the shipped `scheduleRun` plus `verifyGateResults` on a temp workspace: the results file is `[{owner: s2, verdict: pass}, {owner: s1, verdict: fail}]` and verification of a complete owner returns `gate.unproven: … has no recorded passing result (latest verdict fail)`, while the scheduler's state is `passed`. The F22 regression test asserts only the state and the third requester, never the results file, so it stays green.
- Impact: a key that genuinely passed is reported failed by `check` and `check --require-complete`, so the owning task or phase cannot close until the gate is rerun; the scheduler's "reuse the pass" decision and the record ledger disagree on the same key. C5/C6 assume the run state and the record ledger tell one story, so this is F22's class one layer down.
- Suggestion: do not append an authoritative record for an attempt that is no longer last. Either skip `persist` when the terminal-write guard skips (return the local outcome for the caller's report only), or append a `reused: true` record sourced from the state's current `resultIndex` so the effective record remains the newer attempt's pass. Add a regression test that asserts the effective record after A resumes is B's pass, not A's failure.

### F26 — `create --tasks` refuses a three-path scope, and its diagnostic names the wrong fragment

- Severity: Minor
- Location: `packages/specs/src/apps/cli/cli.shared.module.ts:743-750`, `packages/specs/README.md:88-96`, `packages/specs/src/apps/cli/cli.create.module.ts:491-497`
- Status: Resolved
- Attempts: 1
- First Seen: 010
- Problem: the ambiguity refusal fires on any colon-less scope continuation that is not the segment's last fragment (`if (index < fragments.length - 1)`), so a three-path scope is rejected even though a scope list is comma-separated by design. `bun run --cwd packages/specs cli create --tasks "first:execution:scope=app,lib,docs"` exits 1 with `cli.invalid-argument`; the same scope is accepted by `init --task A:first:execution:medium:scope=app,lib,docs` (writes `write-scope: app,lib,docs`) and by `isScopeList` (`scheduler/scope.module.ts:29-35`). The diagnostic is also wrong for this input: it quotes `'first:execution:scope=app,lib'` and says `'lib' could be another scope path or a new task`, then suggests `'first:execution:scope=app;lib'` — `lib` is plainly the second scope path, and the `;` rewrite would keep only `app` in scope while turning `lib` and `docs` into tasks. The help text (`cli.create.module.ts:491-497`) and README (`:88-96`) say a comma inside `scope=` stays in that task's scope list, which is false for the third path; only the README's refusal clause mentions the cut-off.
- Impact: `create --tasks` cannot express a three-or-more-path `write-scope`, so an author leaving `init` for `create` must scaffold the task and hand-edit `TASK.md`; following the printed `fix` silently drops two declared scope paths and creates two phantom tasks, the exact failure class F21/F25 are about. The surface disagrees with `init` and with its own help. The refusal is loud, so an untouched tree is the outcome; the damage comes only from following the suggested rewrite.
- Suggestion: make the rule uniform — every colon-less fragment after a `scope=` field stays in that scope (tasks after a scope list always need `;`), which keeps F25's two-fragment behaviour and accepts `app,lib,docs`; drop the mid-list refusal, or, if the refusal is kept, refuse the whole `scope=` list whenever another fragment follows and name the fragment that could be a task, never a valid scope path. Add `scope=app,lib,docs` to `Cli.scaffoldTaskSpecs grammar` and a `create` test asserting one task with `write-scope: app,lib,docs`.

### F27 — A waiter's reused record is appended outside the run lock, so it can land after a newer attempt's record and decide `check` against the run state

- Severity: Major
- Location: `packages/specs/src/modules/scheduler/scheduler.module.ts:588-620`, `packages/specs/src/modules/scheduler/scheduler.module.ts:683-691`, `packages/specs/src/modules/gates/gates.module.ts:802-807`
- Status: In Review
- Attempts: 1
- First Seen: 011
- Problem: `consume` builds the waiter's outcome from the state it read and then calls `persist(outcome)` (`scheduler.module.ts:618`) with no `RUNS_LOCK_FILE`; only the following `dropWaiter` (`:619`) takes the lock. Nothing revalidates that the consumed attempt is still the last one when the line lands, so a claim and finish for a newer attempt can commit between the state read and the waiter's append. Trigger, reproduced with the shipped `scheduleRun` and `verifyGateResults` on a temp workspace: A (`s1`) runs attempt 1 and fails; W (`s2`), registered as a waiter, wakes on its 50ms poll and consumes A's terminal `failed` state (`:683-691`); while W's `persist` is slow (400ms — the same device the F23 regression uses at `scheduler.test.ts:535` to model a slow append), C (`s3`) sees the failed state, claims attempt 2, passes, and its `finish` appends the pass under the lock and writes `passed` with `resultIndex: 1`. W's reused `fail` line then lands last: the ledger is `[s1 fail, s3 pass, s2 fail reused]`, the state is `passed` with `resultIndex: 1`, and `verifyGateResults({complete: true, owner: 'A001'})` returns `valid: false` with `gate.unproven` — F23's exact impact, produced by the waiter instead of the resumed owner. The inverse reproduces too: A passes, W consumes the pass slowly, C runs attempt 2 with `--no-reuse` and fails; W's reused pass lands after C's fail, so `verifyGateResults` returns `valid: true` while the run state is `failed` — a false green on the latest attempt's failure. A second consequence of the same unlocked append: `appendResult` computes the line index by counting the existing lines, so a waiter append racing a `finish` append to the same `GATE-RESULTS.jsonl` can make one state's `resultIndex` point at the other's record. The regressions miss it: the slow-append test's third requester consumes B's pass with a fast `persist`, and the reclaim test never has a waiter consume a failure, so neither asserts the waiter's line against a newer attempt. `consume`'s own doc comment ("a pass is reused; a failure is not") is contradicted by the waiter path, which consumes terminal failures too.
- Impact: whichever line lands last decides `check` for the stage, independent of the run state and of which attempt actually ran last. A completed task or phase is reported `gate.unproven` and cannot close until the gate is rerun (false red), or is reported proven although its latest attempt failed (false green) — the two stories F23 was filed to reconcile. The trigger is the scheduler's normal parallel case: two `gate run` invocations for the same key, one of which waited, plus a third that reruns after a failure; the window widens with the size of `GATE-RESULTS.jsonl`, since both `readRecordAt` and `appendResult` read the whole file.
- Suggestion: bring the append under the same lock and revalidate before writing — inside `RUNS_LOCK_FILE`, re-read the state and persist only when it still points at the attempt consumed (otherwise return the outcome without a record and let the next `step()` decide) — or skip `persist` for a reused terminal outcome entirely, since the owner's record already proves that attempt and a duplicate line is never authoritative. Either fix also serializes the line index against `finish`. Add a regression: A fails, W waits, C claims attempt 2 and passes while W's persist is slow → keep the state and the effective record on C's pass and `verifyGateResults({complete:true})` valid; plus the `--no-reuse` inverse, where a reused pass must not mask a later failure.

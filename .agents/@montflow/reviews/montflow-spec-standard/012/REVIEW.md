### F27 — A waiter's reused record is appended outside the run lock, so it can land after a newer attempt's record and decide `check` against the run state

- Severity: Major
- Location: `packages/specs/src/modules/scheduler/scheduler.module.ts:588-620`, `packages/specs/src/modules/scheduler/scheduler.module.ts:683-691`, `packages/specs/src/modules/gates/gates.module.ts:802-807`
- Status: Resolved
- Attempts: 1
- First Seen: 011
- Problem: `consume` builds the waiter's outcome from the state it read and then calls `persist(outcome)` (`scheduler.module.ts:618`) with no `RUNS_LOCK_FILE`; only the following `dropWaiter` (`:619`) takes the lock. Nothing revalidates that the consumed attempt is still the last one when the line lands, so a claim and finish for a newer attempt can commit between the state read and the waiter's append. Trigger, reproduced with the shipped `scheduleRun` and `verifyGateResults` on a temp workspace: A (`s1`) runs attempt 1 and fails; W (`s2`), registered as a waiter, wakes on its 50ms poll and consumes A's terminal `failed` state (`:683-691`); while W's `persist` is slow (400ms — the same device the F23 regression uses at `scheduler.test.ts:535` to model a slow append), C (`s3`) sees the failed state, claims attempt 2, passes, and its `finish` appends the pass under the lock and writes `passed` with `resultIndex: 1`. W's reused `fail` line then lands last: the ledger is `[s1 fail, s3 pass, s2 fail reused]`, the state is `passed` with `resultIndex: 1`, and `verifyGateResults({complete: true, owner: 'A001'})` returns `valid: false` with `gate.unproven` — F23's exact impact, produced by the waiter instead of the resumed owner. The inverse reproduces too: A passes, W consumes the pass slowly, C runs attempt 2 with `--no-reuse` and fails; W's reused pass lands after C's fail, so `verifyGateResults` returns `valid: true` while the run state is `failed` — a false green on the latest attempt's failure. A second consequence of the same unlocked append: `appendResult` computes the line index by counting the existing lines, so a waiter append racing a `finish` append to the same `GATE-RESULTS.jsonl` can make one state's `resultIndex` point at the other's record. The regressions miss it: the slow-append test's third requester consumes B's pass with a fast `persist`, and the reclaim test never has a waiter consume a failure, so neither asserts the waiter's line against a newer attempt. `consume`'s own doc comment ("a pass is reused; a failure is not") is contradicted by the waiter path, which consumes terminal failures too.
- Impact: whichever line lands last decides `check` for the stage, independent of the run state and of which attempt actually ran last. A completed task or phase is reported `gate.unproven` and cannot close until the gate is rerun (false red), or is reported proven although its latest attempt failed (false green) — the two stories F23 was filed to reconcile. The trigger is the scheduler's normal parallel case: two `gate run` invocations for the same key, one of which waited, plus a third that reruns after a failure; the window widens with the size of `GATE-RESULTS.jsonl`, since both `readRecordAt` and `appendResult` read the whole file.
- Suggestion: bring the append under the same lock and revalidate before writing — inside `RUNS_LOCK_FILE`, re-read the state and persist only when it still points at the attempt consumed (otherwise return the outcome without a record and let the next `step()` decide) — or skip `persist` for a reused terminal outcome entirely, since the owner's record already proves that attempt and a duplicate line is never authoritative. Either fix also serializes the line index against `finish`. Add a regression: A fails, W waits, C claims attempt 2 and passes while W's persist is slow → keep the state and the effective record on C's pass and `verifyGateResults({complete:true})` valid; plus the `--no-reuse` inverse, where a reused pass must not mask a later failure.

- [Fixer] The reused record is now written in the same critical section it needs. `consume` (`packages/specs/src/modules/scheduler/scheduler.module.ts:605-672`) takes `RUNS_LOCK_FILE` (`:622`), re-reads the state (`:626`), and appends only when the state is still terminal and still describes the consumed attempt (`:632`, via `sameAttempt` at `:316-325`: same phase, same attempt count, same last attempt's session and start instant). The reused `persist` is inside the lock (`:657`) and so is `readRecordAt` (`:635-642`), which orders the pointer read, the line-index computation of `appendResult`, and the record append against `finish`. Trigger: A (`s1`) fails, W (`s2`) consumes slowly, C (`s3`) claims attempt 2 and passes. Inverse: A passes, W's reused pass holds the lock, then C's `--no-reuse` attempt 2 fails and appends last — `state: failed` and the latest record is C's fail, so a reused pass can no longer mask it.

One nuance, benign and not a defect: when a waiter consumes the last attempt's terminal state, its mirrored line is appended after that attempt's own record, so `state.resultIndex` still names the run's own record while `latestResults` picks the later duplicate. The duplicate is built from the pointer record (`exit`, `output`, `durationMs`) or the attempt's own exit fields, so its verdict and exit always equal the pointer's, and the scheduler is the only reader of `resultIndex`; a later attempt's record always lands after the duplicate, so no verdict can be inverted.
